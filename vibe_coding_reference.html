Dev Reference

Vibe Coding & Clean Code
Kapsamlı Başvuru Rehberi

Modern yazılım mimarileri, temiz kod yazma standartları ve AI destekli geliştirme süreçleri (Vibe Coding) için hazırlanmış endüstri standardı başvuru dokümantasyonu.

01. Vibe Coding & Yapay Zeka Destekli Mühendislik

Vibe Coding kavramı: LLM'leri (Yapay zeka dil modellerini) birer kod amelesi gibi değil, üst düzey mimari ortak (AI Collaborator) olarak konumlandırma stratejisidir. Kod yazarken modelle bir "vibe" yakalamak, iteratif ve yüksek verimli bir akışta (flow) çalışmayı ifade eder.

Prompt Engineering Ötesi

Sadece komut vermek yerine, Context Window (Bağlam Penceresi) yönetimini ustalıkla yapmak gerekir. Sisteme "kod kokusu" (code smell) sezdirme teknikleri ve mimari kısıtlamaları proaktif vermek başarıyı artırır.

Trust but Verify

Yapay zekanın halüsinasyonlarına (Hallucinations) karşı körü körüne güvenilmemelidir. AI kodu yazar, ancak sorumluluk her zaman mühendise aittir.

Best Practice (İyi Pratik) AI'a bağlam sunarken tüm projeyi vermek yerine, sadece ilgili modülün, bağımlılıkların ve veri modellerinin özetini sunarak Context Window israfını önleyin.
Code Smell (Kötü Pratik) "Bana şu özelliği yaz" diyerek mimari kararları tamamen LLM'e bırakmak uzun vadede Technical Debt (Teknik Borç) yaratır. 
// Kötü Yaklaşım: AI'dan doğrudan mucize beklemek
// Prompt: "Bana bir kullanıcı yönetim sistemi yaz."

// İyi Yaklaşım: AI Collaborator ile çalışmak
// Prompt: "Elimizde UserRepository ve AuthService interfaceleri var.
// SOLID prensiplerine uygun, Dependency Injection kullanan ve 
// JWT tabanlı token döndüren bir UserLoginService yazar mısın?
// İlgili interface referansları yukarıdadır."

class UserLoginService {
    constructor(userRepository, authService) {
        this.userRepository = userRepository;
        this.authService = authService;
    }

    async login(email, password) {
        // AI tarafından üretilen kontrollü ve mimariye uygun kod
    }
}

02. Clean Code (Temiz Kod) Temelleri

Kodu bilgisayarlar anlasın diye değil, diğer mühendisler anlasın diye yazmalıyız. Kod tabanınız sizinle veya sizden sonra çalışacak kişiler için bir iletişim aracıdır.

İsimlendirme Kuralları

Anlamlı, telaffuz edilebilir ve aranabilir değişken/fonksiyon isimleri kullanın. Sihirli sayılardan (Magic Numbers) ve belirsiz kısaltmalardan kesinlikle kaçının.

Fonksiyon Tasarımı

Tek bir iş yapma (Single Responsibility), kısa tutma ve maksimum 2-3 parametre kuralını uygulayın. Parametre sayısı artıyorsa, bunları bir Obje olarak gruplayın.

Erken Çıkış (Early Return) Koşul ve döngü temizliğinde iç içe geçmiş `if` blokları (Arrow Anti-Pattern) yerine Guard Clauses yaklaşımı ile kodun dikey okunabilirliğini artırın. 
// Kötü Pratik (Code Smell) - İç İçe Geçmiş Bloklar ve Sihirli Sayılar
function check(u) {
    if (u != null) {
        if (u.a > 18) {
            if (u.s === 1) {
                return true;
            }
        }
    }
    return false;
}

// İyi Pratik (Clean Code) - Guard Clauses ve Anlamlı İsimlendirme
const USER_STATUS_ACTIVE = 1;
const LEGAL_AGE = 18;

function isUserEligibleForService(user) {
    // 1. Guard Clauses (Erken Çıkış)
    if (!user) return false;
    if (user.age < LEGAL_AGE) return false;
    if (user.status !== USER_STATUS_ACTIVE) return false;
    
    // 2. Ana mantık
    return true;
}

03. Temel Yazılım Prensipleri (KISS, DRY, YAGNI)

Bu üç prensip, mimari karmaşıklığı dizginlemenin ve sürdürülebilir kod üretmenin temel taşlarıdır. Birlikte uygulandıklarında "Over-engineering" (Aşırı Mühendislik) sorununu ortadan kaldırırlar.

KISS (Keep It Simple, Stupid)

Karmaşık çözümler yerine en sade mimariyi kurma felsefesidir. Kodun zeki görünmesi değil, anlaşılır olması önemlidir.

YAGNI (You Ain't Gonna Need It)

"İleride lazım olur" diye erkenden gereksiz özellikler eklemeyin. Kapsamı dar tutun ve sadece bugünkü ihtiyaçlara odaklanın.

DRY (Don't Repeat Yourself) & İstisnalar Kod tekrarını engelleyin, ancak yanlış soyutlamadan kaçının. Ünlü kural: "Duplication is cheaper than the wrong abstraction" (Tekrar, yanlış bir soyutlamadan daha ucuzdur). 
// YAGNI İhlali - "Belki bir gün lazım olur" diyerek eklenen parametreler
function createReport(data, format = 'pdf', includeCharts = true, 
                      emailTo = null, attachLogs = false, 
                      useNewEngine = false) {
    // Karmaşık ve bakımı zor yapı
}

// KISS ve YAGNI Uygun Tasarım - Sadece bugünün ihtiyacı
function createPdfReport(data) {
    // Basit ve odaklı fonksiyon
    const report = PdfEngine.generate(data);
    return report;
}

04. Yazılım Mühendisliği Kuralları & Teknik Borç

Yazılım geliştirmek sadece kod yazmak değil, aynı zamanda yaşayan bir sistemi yönetmektir. Etik kurallar ve kültür, takım başarısının anahtarıdır.

Boy Scout Rule (İzcilik Kuralı)

Kod tabanını bulduğundan daha temiz bırak. Bir dosyada çalışırken, sadece işini yapıp çıkmak yerine küçük bir değişken ismini düzeltmek bile uzun vadede etkilidir.

Technical Debt (Teknik Borç)

Hızlı ama kirli yazılan kodun gelecekte çıkardığı faiz maliyetidir. Bilinçli alınabilir ancak zamanı geldiğinde Refactoring ile ödenmelidir, aksi takdirde sistemi batırır.

Code Review & Yapay Zeka Entegrasyonu Code Review kültürünü benimseyin. Günümüzde Statik Analiz araçlarına entegre edilen yapay zeka ajanları, PR'larda (Pull Request) potansiyel kod kokularını siz daha commit atmadan tespit edebilir. 
// Teknik Borç Örneği - Geçici Çözüm (Hack)
function calculateTotal(items) {
    // TODO: Vergiyi dinamik olarak DB'den çek, şimdilik statik 1.18 
    // FIXME: 2 yıldır burada duruyor (Teknik Borç Faizi artıyor!)
    return items.reduce((acc, item) => acc + item.price, 0) * 1.18;
}

// İzcilik Kuralı (Boy Scout Rule) İle Borcu Ödeme
async function calculateTotalV2(items, taxService) {
    const taxRate = await taxService.getCurrentRate();
    const subTotal = items.reduce((acc, item) => acc + item.price, 0);
    return subTotal * (1 + taxRate);
}

05. SOLID Tasarım Prensipleri (Derinlemesine)

SOLID prensipleri, esnek, sürdürülebilir ve anlaşılır yazılımlar inşa etmenin temelidir. Kodunuzda "Spaghetti Code" (Spagetti Kod) oluşumunu engeller.

S - Single Responsibility (Tek Sorumluluk)

Bir sınıfın veya modülün değişmek için yalnızca bir nedeni olmalıdır. (Örn: Veritabanı işlemi yapan sınıf, loglama yapmamalıdır.)

O - Open/Closed (Açık/Kapalı)

Yazılım varlıkları genişlemeye açık, değişime kapalı olmalıdır. Yeni bir özellik eklerken mevcut kodu değiştirmeden ekleyebilmelisiniz.

L - Liskov Substitution (Liskov Yerine Geçme)

Alt sınıflar, türedikleri üst sınıfların yerine geçebilmeli ve sistemin beklenen davranışını bozmamalıdır.

I - Interface Segregation (Arayüz Ayrımı)

İstemciler, kullanmadıkları arayüzlere bağımlı olmaya zorlanmamalıdır. Dev bir "God Interface" yerine spesifik küçük interfaceler kullanın.

D - Dependency Inversion (Bağımlılığın Tersine Çevrilmesi)

Yüksek seviyeli modüller, düşük seviyeli modüllere bağlı olmamalıdır. Her ikisi de soyutlamalara (interfaceler) bağlı olmalıdır.

Code Smell (Kötü Pratik) - SRP İhlali Aynı sınıf içerisinde hem iş mantığı, hem UI güncellemeleri, hem de ağ (network) istekleri barındırmak "God Object" anti-paternidir. 
// Kötü Pratik (Open/Closed İhlali)
function getDiscount(userType) {
    if (userType === "GOLD") return 0.2;
    if (userType === "SILVER") return 0.1;
    // Yeni bir üye tipi eklendiğinde bu kodu DEĞİŞTİRMEK zorundayız!
    return 0;
}

// İyi Pratik (Open/Closed Prensibine Uygun - Genişlemeye Açık)
const discountStrategies = {
    "GOLD": () => 0.2,
    "SILVER": () => 0.1,
    "PLATINUM": () => 0.3 // Mevcut fonksiyonu ellemeden yeni tip eklendi
};

function getDiscountV2(userType) {
    const strategy = discountStrategies[userType];
    return strategy ? strategy() : 0;
}

06. Mimari Desenler & Sistem Tasarımı

Bir uygulamanın performansı, ölçeklenebilirliği ve dayanıklılığı seçilen mimariye bağlıdır. Mimari, sadece kodun dizilimi değil, sistemin nasıl iletişim kurduğudur.

Monolit vs Mikroservis

Her şeye doğrudan mikroservis ile başlamak "Microservice Premium" maliyetini ödemektir. Çoğu proje iyi yapılandırılmış modüler bir Monolit (Modular Monolith) ile başlamalıdır.

Idempotency (Eşetkililik)

Dağıtık sistemlerde aynı ağ isteğinin (retry vb. sebeplerle) birden fazla kez işlenmesi veri tutarsızlığı yaratmamalıdır. Sistem bu duruma karşı bağışık tasarlanmalıdır.

Katmanlı Mimari (Layered Architecture) Presentation (Sunum), Business (İş Mantığı) ve Data Access (Veri Erişimi) katmanlarını kesin hatlarla ayırın. Bir katmandaki değişiklik diğerini kırmamalıdır. 
// Idempotency Örneği (İşlem Güvenliği)

// Kötü Yaklaşım: Aynı istek iki kere gelirse bakiye 2 kere düşer!
async function processPayment(userId, amount) {
    await db.users.decrementBalance(userId, amount);
    return { status: 'success' };
}

// İyi Yaklaşım: Idempotency Key ile tekrarı önleme
async function processPaymentV2(userId, amount, idempotencyKey) {
    const existingTx = await db.transactions.findByKey(idempotencyKey);
    if (existingTx) return existingTx.result; // Daha önce işlenmişse eski sonucu dön

    await db.users.decrementBalance(userId, amount);
    const result = { status: 'success', txId: generateId() };
    
    await db.transactions.save(idempotencyKey, result);
    return result;
}

07. Hata Yönetimi & Dayanıklılık

Hatalar sistemin doğal bir parçasıdır. Önemli olan hatanın olmaması değil, sistemin hataya nasıl tepki verdiğidir.

Silence is Fatal (Hataları Yutmayın)

Boş `catch` blokları, sistemde saatli bir bomba bırakmak gibidir. Hatayı yutmak, kök neden analizini (Root Cause Analysis) imkansız kılar.

Graceful Degradation

Sistemin bir parçası çöktüğünde tüm sistem çökmemelidir. İkincil servisler (Örn: Öneri motoru) çalışmazsa, ana akış (Satın alma) devam edebilmelidir.

Circuit Breaker (Devre Kesici) Deseni Bir dış servise yapılan istekler sürekli zaman aşımına uğruyorsa, devreyi keserek (istek atmayı durdurarak) servise toparlanma süresi verilmeli ve kendi sistemimizin kilitlenmesi önlenmelidir. 
// Kötü Pratik (Hata Yutma)
try {
    saveToDatabase(data);
} catch (error) {
    // BOMBOŞ CATCH: Ne log var ne aksiyon! Sistem sessizce patlar.
}

// İyi Pratik (Graceful Handling & Re-throwing)
try {
    saveToDatabase(data);
} catch (error) {
    Logger.error("Veritabanı kayıt hatası", { error, dataId: data.id });
    
    // Eğer kritik bir hataysa üst katmana fırlat (Fail Fast)
    if (error instanceof ConnectionError) {
        throw new AppError("Sistem geçici olarak kullanılamıyor", 503);
    }
}

08. Test Güdümlü Geliştirme (TDD) & Otomasyon

Testler sadece kodun çalıştığını kanıtlamaz, aynı zamanda kodun kullanım kılavuzu ve güven ağıdır.

Red-Green-Refactor Döngüsü

Önce testi yaz (Kırmızı - Başarısız), sonra kodu sadece testi geçecek kadar yaz (Yeşil - Başarılı), son olarak tasarımı iyileştir (Refactor).

%100 Coverage Tuzağı

Test kapsayıcılığının (Coverage) %100 olması kodun hatasız olduğu anlamına gelmez. Anlamsız get/set metotlarını test etmek yerine, kritik iş kurallarını (Business Logic) test edin.

Birim Testleri (Unit Tests) & Clean Code Eğer bir fonksiyon için Unit Test yazmak çok zorsa (mocking cehennemi varsa), bu fonksiyon muhtemelen çok fazla iş yapıyordur (SRP İhlali). Test zorluğu bir Code Smell göstergesidir. 
// AAA Pattern (Arrange - Act - Assert) ile Test Yazımı
describe('DiscountService', () => {
    it('should apply 10% discount for premium users', () => {
        // Arrange (Hazırlık)
        const user = { type: 'PREMIUM' };
        const cartTotal = 100;
        
        // Act (Eylem)
        const finalPrice = DiscountService.calculate(user, cartTotal);
        
        // Assert (Doğrulama)
        expect(finalPrice).toBe(90);
    });
});

09. AI Destekli Refactoring (Yeniden Yapılandırma)

Refactoring, mevcut kodun dış davranışını değiştirmeden iç yapısını iyileştirme sanatıdır. Vibe Coding çağında AI, legacy kodları modernize etmek için en güçlü silahtır.

Güvenli Refactoring İçin

Yapay zekaya refactor komutu vermeden önce o modülün testlerinin tam (Regression Tests) olduğundan emin olun. Testi olmayan kodu yapay zekaya emanet etmek Rus Ruleti oynamaktır.

Küçük Adımlar (Baby Steps)

Devasa dosyaları tek seferde refactor etmek yerine, fonksiyon fonksiyon ayırarak ilerleyin. AI modellerinin "Context Window" sınırı nedeniyle parça parça işlemek daha etkilidir.

// AI Refactoring Prompt Örneği:
/* 
"Aşağıdaki calculate_invoice_v2 isimli fonksiyon Spagetti kod haline gelmiş 
durumda ve çok fazla yan etkisi (side-effect) var. 
Mevcut Unit Testleri kırmadan, bu fonksiyonu 'Fonksiyonel Programlama' (Pure functions) 
prensiplerine göre 3 küçük yardımcı fonksiyona bölerek yeniden yaz (Refactor).

10. Versiyon Kontrolü (Git) & Takım İletişimi

Git geçmişiniz projenizin günlüğüdür. Sadece sizin değil, aylar sonra o koda bakan takım arkadaşınızın da (veya yapay zeka aracının da) ne yapıldığını anlaması gerekir.

Conventional Commits

Commit mesajlarında standart bir dil kullanın (Örn: `feat:`, `fix:`, `refactor:`, `docs:`). Bu sayede changelog (değişiklik notları) otomatik oluşturulabilir.

Trunk-Based Development

Git-Flow'un getirdiği karmaşık dal (branch) yapısı yerine, kısa ömürlü dallar ve hızlı entegrasyonlar (Continuous Integration) ile ana dala (main/trunk) sürekli kod gönderme stratejisi.

Kötü Commit Mesajları "fixledim", "hata çözüldü", "update", "wip" gibi mesajlar projenin izlenebilirliğini yok eder. 
# Kötü Pratik
git commit -m "Login hatasını düzelttim"

# İyi Pratik (Conventional Commits Standartı)
git commit -m "fix(auth): JWT token expiration time parsing bug"
# - Ne yapıldı? fix (hata çözümü)
# - Hangi kapsamda? auth modülü
# - Hata neydi? JWT bitiş süresi ayrıştırma hatası

11. CI/CD Pipeline & Otomatik Emniyet Süreçleri

İnsanlar hata yapar, sistemler yapmamalıdır. Temiz kod standartlarını insan inisiyatifinden çıkarıp CI/CD pipeline'larına entegre etmek kalıcı başarı sağlar.

Linting & Formatting Gatekeeper

Kodu depoya göndermeden önce ESLint, Prettier, Flake8 gibi araçlar otomatik çalışmalı, standartlara uymayan kodlar ana dala girememelidir (Git Pre-commit hooks).

Continuous Deployment (CD)

Her onaylanan PR'ın otomatik testlerden geçtikten sonra test/staging ortamına hatta production'a güvenli bir şekilde (Canary release) dağıtılması (deploy) gerekir.

# Örnek GitHub Actions CI Pipeline Kesiti
name: CI Pipeline

on: [push, pull_request]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Linter Check
        run: npm run lint
      - name: Unit Tests & Coverage
        run: npm run test -- --coverage
      - name: Block if coverage drops below 80%
        run: ./check-coverage.sh 80

12. Sürdürülebilirlik & Dokümantasyon

Hiçbir kod sonsuza kadar yaşamaz, ancak iyi dokümante edilmiş bir projenin devri ve evrimi çok daha sancısız olur.

Kod Kendini Anlatmalı

Aşırı yorum (comment) yazmak iyi bir şey değildir. Eğer kod "Ne" yaptığını anlatamıyorsa, koda yorum eklemek yerine kodu daha okunabilir hale getirecek şekilde refactor edin. Yorumlar "Neden" (Why) yapıldığını açıklamalıdır.

AI İçin Architecture Docs

Artık dokümantasyonu sadece insanlar değil, AI ajanları da okuyor. Proje kök dizininde `ARCHITECTURE.md` veya `AI_PROMPT.md` bulundurarak sistemin mimari kurallarını modellere proaktif olarak öğretin.

API Dokümantasyonu (Swagger/OpenAPI) API dokümantasyonunu elle word/pdf dosyalarında yazmayın. Kodu referans alan ve dinamik güncellenen Swagger (OpenAPI) entegrasyonları ile her zaman güncel tutun. 
// Kötü Yorum Pratiği ("Ne" yapıldığını açıklayan gereksiz yorum)
// Kullanıcı aktifse true döner
if (user.status === 1) { return true; }
