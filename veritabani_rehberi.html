DB Reference

01. İlişkisel Veritabanı Temelleri (PK, FK)

İlişkisel veritabanları (RDBMS), verileri tablolar halinde tutar ve bu tablolar arasındaki bağlantıları matematiksel bir doğrulukla (Relational Algebra) yönetir. Doğru bir mimari kurmanın en temel taşı bu kısıtlamaları (constraints) anlamaktır.

Primary Key (PK) & Foreign Key (FK)

Primary Key (Birincil Anahtar): Bir tablodaki her kaydı tekil (unique) yapan benzersiz tanımlayıcıdır. Asla NULL olamaz.

Foreign Key (Yabancı Anahtar): Başka bir tablonun PK'sine referans veren sütundur. Veri bütünlüğünü (Referential Integrity) sağlar; yani var olmayan bir kayda referans verilmesini engeller.

SQL DDL Örneği (PostgreSQL)
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    total DECIMAL(10,2) NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

02. Veri Modelleme ve SQL İlişkileri

One-to-One (1:1) İlişkiler

Bir tablodaki bir kaydın, diğer tabloda sadece bir kaydı olduğu durumdur. Genellikle devasa tabloları (örneğin kullanıcı detaylarını) ana tablodan ayırmak için (Vertical Partitioning) kullanılır.

CREATE TABLE user_profiles (
    id SERIAL PRIMARY KEY,
    user_id INT UNIQUE NOT NULL, -- UNIQUE kısıtlaması 1:1 ilişkiyi garanti eder!
    bio TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id)
);

One-to-Many (1:N) İlişkiler

En yaygın ilişki türüdür. Bir satır, başka tablodaki birçok satırla ilişkili olabilir (örneğin 1 Kullanıcının N tane Siparişi olması gibi). FK her zaman "Many" olan (N) tabloya konur.

Many-to-Many (N:M) İlişkiler

Bir kitabın birden fazla yazarı olabileceği ve bir yazarın birden fazla kitabı olabileceği durumdur. SQL'de bu ilişki doğrudan kurulamaz; araya bir Junction (Pivot) Table konulması gerekir.

CREATE TABLE book_authors (
    book_id INT NOT NULL,
    author_id INT NOT NULL,
    PRIMARY KEY (book_id, author_id), -- Composite PK
    FOREIGN KEY (book_id) REFERENCES books(id),
    FOREIGN KEY (author_id) REFERENCES authors(id)
);

03. ER Diyagramları ve Crow's Foot Notasyonu

Veritabanı tasarımını koda dökmeden önce görselleştirmek için ER (Entity-Relationship) diyagramları kullanılır. Endüstri standardı olan notasyon ise Crow's Foot (Karga Ayağı) notasyonudur.

Sembollerin Anlamları:
| | (İki Çizgi): Exactly One (Kesinlikle 1)
0 | (Sıfır ve Çizgi): Zero or One (0 veya 1)
> | (Karga Ayağı ve Çizgi): One or Many (1 veya Çok)
> 0 (Karga Ayağı ve Sıfır): Zero or Many (0 veya Çok)
erDiagram USERS ||--o{ ORDERS : "places" USERS { int id PK string email } ORDERS { int id PK int user_id FK decimal total } BOOKS ||--|{ BOOK_AUTHORS : "has" AUTHORS ||--|{ BOOK_AUTHORS : "writes" BOOK_AUTHORS { int book_id FK int author_id FK }

04. Modern Geliştirici Araçları

Görsel No-Code Araçlar

Günümüzde tabloları SQL ile değil, dbdiagram.io veya DrawSQL gibi araçlarla görsel olarak (veya DBML kullanarak) tasarlamak çok yaygındır. Bu araçlar ER diyagramını çizer ve SQL DDL kodunu otomatik üretir.

Prisma ORM ile Deklaratif Modelleme

Prisma gibi modern ORM'ler, SQL tablolarını nesnelere dönüştürür. schema.prisma dosyası kullanılarak ilişkiler çok daha okunabilir bir syntax ile yazılır.

schema.prisma Örneği (1:N İlişki)
model User {
  id      Int      @id @default(autoincrement())
  email   String   @unique
  orders  Order[]  // Prisma ilişkisi (1:N)
}

model Order {
  id      Int      @id @default(autoincrement())
  total   Decimal
  user    User     @relation(fields: [userId], references: [id])
  userId  Int      // Yabancı Anahtar (FK)
}

05. Veritabanı Paradigmalari: SQL vs. NoSQL

Veri mimarisinin en temel karar noktası olan SQL ve NoSQL sistemlerinin felsefeleri ve veri işleme modelleri.

İlişkisel Model (SQL)

Verileri önceden tanımlanmış katı bir şemada (schema) ve tablolar halinde saklar. ACID prensiplerini tam olarak destekleyerek veri bütünlüğünü garanti altına alır. Oracle, PostgreSQL ve MySQL endüstri standartlarıdır.

ACID Anatomisi Atomicity (Ya hep ya hiç), Consistency (Geçerli veri), Isolation (İşlem yalıtımı), Durability (Kalıcılık). Bu dörtlü, finansal veya kritik sistemlerde verinin asla yarı yolda kalmamasını veya bozulmamasını güvence altına alır.
relational_schema.sql 
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(id),
    total_amount DECIMAL(10, 2) NOT NULL,
    status VARCHAR(20) DEFAULT 'pending'
);

NoSQL Modelleri (Document, Key-Value, Graph)

Başlangıçta "Non-Relational SQL" (İlişkisel Olmayan SQL) olarak ortaya çıksa da günümüzde yaygın olarak "Not Only SQL" (Sadece SQL Değil) şeklinde adlandırılan NoSQL; ilişkisel olmayan, esnek şemalı ve yatayda kolayca ölçeklenebilen veritabanı sistemlerini tanımlar. MongoDB, Redis ve Cassandra gibi öne çıkan NoSQL sistemleri, yüksek ölçeklenebilirlik ihtiyaçlarına yanıt vermek üzere tasarlanmış olup BASE (Basically Available, Soft state, Eventual consistency) felsefesini temel alır.

CAP Teoremi Uyarısı Bir dağıtık sistem aynı anda hem Consistency (Tutarlılık), hem Availability (Erişilebilirlik) hem de Partition Tolerance (Bölünme Toleransı) sağlayamaz. NoSQL sistemleri yatay ölçeklenirken genellikle Consistency'den ödün verir (AP sistemler).
document_store.js 
// MongoDB Document Model - Esnek yapı, Join yerine gömülü veriler
db.orders.insertOne({
    "user_id": ObjectId("5f4e3d2c1b"),
    "total_amount": 150.50,
    "items": [
        { "product": "Laptop", "qty": 1 },
        { "product": "Mouse", "qty": 2 }
    ],
    "status": "pending"
});

Neo4j ve Grafik (Graph) Tabanlı NoSQL

Veriler düğüm (node) ve kenar (edge/relationship) olarak modellenir. Kenarlar da özellikler (properties) taşıyabilir. Grafik veritabanları, özellikle derinlemesine gezinme (traversal) sorgularında ilişkisel veritabanlarını çok geride bırakır; çünkü JOIN yerine doğrudan işaretçi (pointer) takibi kullanır.

Ne zaman tercih edilmeli? Sosyal ağlar, öneri motorları (recommendation engine), dolandırıcılık tespiti, erişim kontrol grafikleri ve bilgi grafikleri (knowledge graph) gibi ilişkilerin kendisinin birinci sınıf veri olduğu senaryolarda Neo4j rakipsizdir.

06. İndeksleme Mekanizmaları & B-Tree Anatomisi

Veritabanı performansının belkemiği olan indeks yapıları ve B-Tree algoritmalarının çalışma mantığı.

B-Tree ve B+Tree Ağaç Yapıları

Modern veritabanları (PostgreSQL, MySQL InnoDB) indeksleri B-Tree veya B+Tree yapısında tutar. Veriler dengeli bir ağaçta (balanced tree) yaprak düğümlere (leaf nodes) kadar sıralı şekilde saklanarak milyonlarca satırda bile arama maliyeti O(log n)'e düşürülür.

Clustered vs. Non-Clustered Index Clustered (Kümelenmiş) indeksler, verinin diskteki fiziksel dizilişini belirler. Bir tabloda sadece bir adet olabilir (genellikle Primary Key). Non-Clustered indeksler ise ayrı bir yapıda saklanıp verinin referansını (pointer) işaret eder.

Composite (Bileşik) İndeksler ve Tuzaklar

Birden fazla sütunu kapsayan indekslerdir. İndeksin kullanılabilmesi için sorgunun "Left-to-Right" (Soldan Sağa) kuralına uyması gerekir.

Query Smell: "Left-to-Right" İhlali Eğer bir indeks (A, B, C) sütunları üzerindeyse, sadece B veya C ile yapılan WHERE sorguları bu indeksi kullanamaz (Full Table Scan yapar). Sorgu mutlaka A'dan başlamalıdır. Ayrıca istenen tüm sütunlar indekste varsa buna "Cover Index" denir ve tabloya hiç gidilmeden çok yüksek hızla cevap dönülür.
composite_index.sql 
-- İndeks Tanımlaması (status ve created_at)
CREATE INDEX idx_user_status_date ON users(status, created_at);

-- İndeksi KULLANAN mükemmel sorgu
SELECT id FROM users WHERE status = 'active' AND created_at > '2023-01-01';

-- İndeksi KULLANAMAYAN hatalı sorgu (Sadece 2. sütuna filtre verilmiş)
SELECT id FROM users WHERE created_at > '2023-01-01';

07. Sorgu Optimizasyonu & Execution Plan Okuma

SQL Optimizer kararlarını anlamak ve darboğazları tespit etmek için Execution Plan (Çalıştırma Planı) okuma teknikleri.

Veritabanı Motoru Aşamalari

Bir sorgu DB'ye ulaştığında sırasıyla: Parser (Sözdizimi kontrolü), Optimizer (En düşük maliyetli yolu bulma) ve Execution Engine (Fiziksel olarak veriyi getirme) adımlarından geçer.

Performance Tip: Table Scan vs Index Scan Execution Plan'da Seq Scan (veya Table Scan) görmek tablonun diskte baştan sona okunduğunu gösterir. Milyonluk tablolarda bu bir felakettir. Index Scan veya Index Only Scan hedeflenmelidir.

Anti-Pattern'ler ve EXPLAIN Analizi

N+1 sorgu problemi, OR operatörünün indeks kullanımını iptal etmesi, yanlış JOIN hiyerarşileri en sık yapılan hatalardır.

Query Smell: SELECT * Kullanımı Sadece ihtiyacınız olan sütunları çekin. "SELECT *" kullanımı, veritabanının "Index Only Scan" yapmasını engeller, ağ (network) üzerinde gereksiz bant genişliği harcar ve bellek (RAM) şişmesine neden olur.
explain_analyze.sql 
-- Sorgunun arka plandaki tahmini maliyetini (cost) ve gerçek çalışma süresini görme
EXPLAIN ANALYZE 
SELECT u.username, o.total_amount 
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.status = 'active';

/* İdeal Çıktı Örneği:
-> Nested Loop  (cost=0.56..12.34 rows=50 width=24) (actual time=0.015..0.025 rows=30 loops=1)
   -> Index Scan using idx_user_status on users u ...
   -> Index Scan using idx_order_user on orders o ...
*/

08. Eşzamanlılık Kontrolü, Kilitler & Deadlock

Aynı anda çalışan yüzlerce transaction'ın birbirini ezmesini engelleyen kilit mekanizmaları ve izolasyon seviyeleri.

İzolasyon Seviyeleri (Isolation Levels)

ACID'deki "I" (Isolation) prensibinin dozunu ayarlar. Seviye arttıkça veri güvenliği artar fakat performans/eşzamanlılık düşer.

  • Read Uncommitted: Dirty Read (Kirli okuma) yapabilir. Başka işlemin bitmemiş yazmasını okur. En hızlı ama en güvensiz.
  • Read Committed: Dirty Read engellenir. PostgreSQL ve Oracle'ın default seviyesidir.
  • Repeatable Read: Non-repeatable Read engellenir. Okunan veri transaction bitene kadar asla değişmez. MySQL InnoDB defaultudur.
  • Serializable: Phantom Read de engellenir. Tüm transaction'lar sıraya sokulur. En yavaş ama en güvenli seviyedir.
Lock (Kilit) Tipleri Shared Lock (S): Veriyi okumak için alınır. Başka okuyuculara izin verir, yazıcıları bekletir.
Exclusive Lock (X): Veriyi değiştirmek (UPDATE/DELETE) için alınır. Kimseyi yaklaştırmaz.

Deadlock (Kilitlenme) Problemi

İki işlemin birbirinin elindeki kilitli kaynağı (Row veya Table Lock) beklemesi sonucu oluşan sonsuz döngüdür. Veritabanı motoru deadlock durumunu saniyeler içinde algılar ve bir işlemi "kurban" (victim) seçerek işlemi iptal (rollback) eder.

Deadlock Önleme İpucu Tablolara ve satırlara her zaman aynı hiyerarşik sırayla (örneğin her zaman önce Users tablosuna, sonra Orders tablosuna lock atılmalı) erişecek şekilde transaction'larınızı tasarlayın. Tablo bazlı devasa kilitler yerine her zaman Satır bazlı (Row-level) işlemler yapın.
deadlock_scenario.sql 
-- TRANSACTION A:
BEGIN;
UPDATE users SET balance = balance - 100 WHERE id = 1;  -- (Satır 1 kilitlendi)
-- ...bekleme...
UPDATE accounts SET amount = amount + 100 WHERE user_id = 2; -- (Satır 2'yi istiyor)

-- TRANSACTION B:
BEGIN;
UPDATE accounts SET amount = amount - 100 WHERE user_id = 2; -- (Satır 2 kilitlendi)
-- ...bekleme...
UPDATE users SET balance = balance + 100 WHERE id = 1; -- (Satır 1'i istiyor)

-- SONUÇ: ORA-00060 (Oracle) veya ERROR 1213 (MySQL) - Deadlock found!

09. Büyük Ölçekli Veri Yönetimi: Replication & Sharding

Sistem trafiği artıp tek bir sunucunun kapasitesini aştığında devreye giren yatay ölçeklendirme (Horizontal Scaling) stratejileri.

Replication (Replikasyon) Mimarisi

Verinin güvenliğini artırmak ve okuma (read) yükünü dağıtmak için veritabanının kopyalarının oluşturulması işlemidir.

  • Master-Slave (Primary-Replica): Yazma işlemleri (INSERT/UPDATE) sadece Master'a yapılır. Okuma işlemleri (SELECT) Slave sunuculara dağıtılarak Read-Heavy (okuma ağırlıklı) sistemler rahatlatılır.
  • Multi-Master: Birden çok sunucuya yazma yapılabilir. Çatışma çözümü (Conflict Resolution) zordur fakat yüksek yazma erişilebilirliği sağlar.
Architecture Note: Senkron vs. Asenkron Replikasyon Senkron replikasyonda Master, Slave'den "veriyi yazdım" onayı almadan işlemi bitirmez (çok güvenli ama yavaş). Asenkron replikasyonda ise beklemez (çok hızlı ama Master çökerse veri kaybı riski var).

Sharding (Yatay Bölümleme)

Devasa bir veritabanının fiziksel olarak farklı sunuculara (Shard) parça parça dağıtılmasıdır. Sistem sonsuz ölçeklenebilir hale gelir.

Architecture Note: Sharding Key Seçimi ve Hotspot Eğer Shard Key olarak ardışık artan bir değer (örneğin timestamp veya auto-increment ID) seçerseniz, tüm yeni kayıtlar aynı sunucuya (Hotspot) gider ve diğer sunucular yatar. Hash-based (kriptografik dağıtım) genellikle en dengeli yük dağılımını sağlar.
sharding_concept.js 
// Basit Hash-Based Sharding Mantığı
function getShardForUser(userId) {
    const totalShards = 4;
    // Kullanıcı ID'sinin hash'inin modunu alarak sunucuyu bul
    const shardIndex = hashFunction(userId) % totalShards;
    return `db_shard_${shardIndex}`;
}

10. PostgreSQL İleri Düzey Özellikleri (JSONB & Partitioning)

PostgreSQL'in sadece ilişkisel bir DB olmanın ötesine geçerek NoSQL yeteneklerini ve Big Data yönetimini sağlayan özellikleri.

Yarı-İlişkisel Güç: JSON vs JSONB

PostgreSQL, JSON verileri metin (JSON) veya binary formatta (JSONB) saklayabilir. JSONB formatı ayrıştırılarak saklandığı için yazarken biraz yavaştır fakat okurken inanılmaz hızlıdır ve indekslenebilir (GIN Index).

Performance Tip: GIN Index ile JSON Araması JSON dokümanlarının içindeki key-value eşleşmelerini tam metin araması (Full-text) hızında bulmak için Generalized Inverted Index (GIN) kullanılır.
postgres_jsonb.sql 
-- JSONB sütununa GIN Index ekleme
CREATE INDEX idx_user_metadata ON users USING GIN (metadata);

-- Hızlı JSON sorgusu (@> operatörü "içerir mi" anlamına gelir)
SELECT id, username 
FROM users 
WHERE metadata @> '{"role": "admin", "skills": ["SQL"]}';

-- JSON içindeki spesifik bir değere erişim (->>)
SELECT metadata->>'company' AS company_name FROM users;

Table Partitioning (Tablo Bölümleme)

Milyarlarca satırlık tek bir tabloyu mantıksal olarak alt tablolara (partition) bölme işlemidir. Range (tarihe göre), List (kategoriye göre) ve Hash partitioning türleri vardır.

Architecture Note: DROP PARTITION Avantajı Geçmiş verileri silmek (DELETE) işlemi, tabloda "Dead Tuple" yaratır ve tabloyu kilitler. Ancak partitioning kullanıldığında, eski aya ait tabloyu silmek (DROP TABLE) anında gerçekleşir ve performansa sıfır etki eder.
partitioning.sql 
-- Ana Tablonun Tarih (Range) bazlı bölümleneceğinin ilanı
CREATE TABLE logs (
    id SERIAL,
    log_level VARCHAR(10),
    created_at DATE NOT NULL
) PARTITION BY RANGE (created_at);

-- Aylık alt tabloların (Partition) oluşturulması
CREATE TABLE logs_2023_01 PARTITION OF logs 
    FOR VALUES FROM ('2023-01-01') TO ('2023-02-01');

11. MongoDB & Doküman Tabanlı Veri Modelleme

Esnek şema ve doküman tabanlı NoSQL veritabanı tasarım felsefesi ile ilişkisel dünyanın ötesindeki stratejiler.

İlişki Modelleme: Embedding vs Referencing

MongoDB'de JOIN işlemleri maliyetli olduğu için veriler genellikle iç içe (Embedded) tutulur. Ancak veri boyutuna ve büyüme hızına göre karar verilmelidir.

  • Embedding (Gömme): Adresler veya Telefon numaraları gibi ana dokümana sıkı sıkıya bağlı ve sınırlı sayıda olan veriler için idealdir.
  • Referencing (Referans Gösterme): Bir yazarın on binlerce kitabı olması gibi ilişkilerin sınırsız büyüyebileceği (Unbounded) durumlarda, ObjectID ile referans verilmelidir.

Aggregation Framework

MongoDB'nin karmaşık veri analitiği ve raporlama işlemlerini arka arkaya bağlanan boru hatları (pipeline) ile çözmesini sağlayan güçlü motorudur.

Performance Tip: Sıralama Önemlidir Aggregation pipeline'ında her zaman önce $match (WHERE karşılığı) kullanılmalıdır. Böylece sonraki aşamalara giden veri seti en başından küçültülmüş olur.
aggregation.js 
// 2023'te kayıt olan aktif kullanıcıların, satın aldıkları ürünlerin toplam cirosu
db.users.aggregate([
    // 1. Filtreleme (WHERE)
    { $match: { status: "active", join_year: 2023 } },
    
    // 2. Başka tablo ile Join (LEFT OUTER JOIN)
    { $lookup: {
        from: "orders",
        localField: "_id",
        foreignField: "user_id",
        as: "user_orders"
    }},
    
    // 3. Array'i düzleştirme (Array içindeki her eleman için yeni satır yaratma)
    { $unwind: "$user_orders" },
    
    // 4. Gruplama ve Toplama (GROUP BY ve SUM)
    { $group: {
        _id: "$_id",
        username: { $first: "$username" },
        total_spent: { $sum: "$user_orders.amount" }
    }},
    
    // 5. Sıralama (ORDER BY DESC)
    { $sort: { total_spent: -1 } }
]);

12. Redis & Önbellekleme (Caching) Stratejileri

Sistem yanıt sürelerini milisaniyelere düşüren In-Memory (bellek içi) veri yapısı sunucusu ve Caching mimarileri.

Caching Patterns (Önbellek Kalıpları)

Veritabanı yükünü hafifletmek için verinin RAM'de (Redis) tutulma stratejileri.

  • Cache-Aside (Lazy Loading): Uygulama önce Redis'e bakar. Yoksa veritabanına gider, veriyi alır, Redis'e yazar ve kullanıcıya döner. En yaygın modeldir.
  • Write-Through: Veri her zaman önce Cache'e yazılır, Cache anında veritabanına yazar. Veri her zaman günceldir ama yazma işlemi biraz yavaşlar.
  • Write-Behind (Write-Back): Veri sadece Cache'e yazılır ve kullanıcıya anında cevap dönülür. Cache, belirli aralıklarla (asenkron) veriyi veritabanına topluca kaydeder (Yüksek yazma hızı, yüksek veri kaybı riski).

Kritik Önbellek Problemleri

Kötü tasarlanmış bir önbellek mimarisi sistemin tamamen çökmesine neden olabilir.

Architecture Note: Cache Avalanche & Penetration

Cache Avalanche (Önbellek Çığı): Binlerce Cache anahtarının (Key) aynı anda süresinin dolması (TTL expire) sonucu veritabanına aniden devasa yük binmesidir. Çözüm: TTL sürelerine rastgele (random) saniyeler eklemektir.

Cache Penetration: Veritabanında olmayan (örneğin id=-1) bir verinin sürekli sorgulanıp doğrudan veritabanına yük bindirmesidir. Çözüm: Olmayan verileri de Redis'te "NULL" olarak kısa süreliğine (örneğin 30sn) cache'lemektir.
redis_commands.sh 
# Redis Temel Veri Tipleri ve TTL (Time-To-Live) Kullanımı

# 1. String - Standart Cache (EX: 3600 sn sonra silinir)
SET user:profile:105 '{"name": "Ali", "role": "Admin"}' EX 3600

# 2. Hash - Obje özellikleri tutma
HSET product:501 name "Laptop" price 1500 stock 45

# 3. Sorted Set - Liderlik tablosu (Score'a göre otomatik sıralar)
ZADD gaming:leaderboard 5400 "player_1"
ZADD gaming:leaderboard 7200 "player_2"
# En yüksek skorlu 10 oyuncuyu getir
ZREVRANGE gaming:leaderboard 0 9 WITHSCORES

13. Veri Ambarı (Data Warehouse) & Devasa Sütun Tabanlı Sistemler (ClickHouse)

Terabaytlarca veriyi saniyeler içinde analiz etmemizi sağlayan analitik (OLAP) sistemlerin mimari farklılıkları.

OLTP vs. OLAP ve Sütun Tabanlı Mimari

Geleneksel veritabanları (OLTP) veriyi satır satır (Row-oriented) yazar; bu "Insert" işlemleri için harikadır ama "Tüm kullanıcıların yaş ortalaması nedir?" gibi analitik (OLAP) sorgularda tüm tabloyu okuması gerekir. Sütun tabanlı (Column-oriented) veritabanları (ClickHouse, BigQuery) veriyi sütunlar halinde depolar. Böylece sadece "Yaş" sütunu diskten okunur ve olağanüstü performans (100x) elde edilir.

Production Note: Vektörel İcra ve Sıkıştırma Sütun tabanlı mimarilerde aynı tipte veriler (örneğin binlerce integer yaş verisi) arka arkaya durduğu için çok yüksek oranda sıkıştırılır. ClickHouse bu sıkıştırılmış veriyi işlemcide vektörel (SIMD) komut setleriyle paralel işleyerek hızı 1000x'e kadar çıkarır.

Veri Ambarı Modellemesi

Analitik sistemlerde ilişkisel veritabanı kuralları (Normalizasyon) esnetilir. Milyarlarca satırlık FACT (Olay/Satış) tabloları ile bunları açıklayan DIMENSION (Müşteri/Ürün) tabloları tasarlanır.

  • Star Schema (Yıldız Şema): Ortada devasa bir Fact tablosu, etrafında birincil Dimension tabloları. Join sayısı azdır, performanslıdır.
  • Snowflake Schema (Kar Tanesi Şema): Dimension tabloları kendi içlerinde tekrar normalize edilir. Join sayısı artar, sorgular yavaşlar fakat alan tasarrufu sağlar.

14. Veritabanı Migration Yönetimi (Flyway/Liquibase)

Yazılım kodunun Git ile versiyonlanması gibi, veritabanı şemasının da zaman içindeki değişimini (Schema Evolution) güvenle yönetme sanatı.

Otomatik Migration Mantığı

"Kod Git'te, DB nerede?" sorunsalını çözmek için Flyway veya Liquibase kullanılır. Araç, veritabanında schema_version isimli bir tablo oluşturur ve hangi script'lerin (SQL dosyalarının) çalıştırıldığını takip eder.

DevOps Tip: Zero-Downtime Migration Canlı sistemde bir sütunun adını doğrudan değiştirmek (RENAME COLUMN) sistemi çökertir. Bunun yerine Expand/Contract (Genişlet/Daralt) kalıbı kullanılır:

1. Yeni sütunu ekle (Expand)
2. Kodu hem eskiye hem yeniye yazacak şekilde güncelle
3. Eski verileri yeni sütuna taşı
4. Kodu sadece yeni sütunu okuyacak şekilde güncelle
5. Eski sütunu sil (Contract)
V2__add_status_column.sql 
-- Flyway isimlendirme standardı: V[Versiyon]__[Açıklama].sql
-- Örnek: V1__init.sql, V2__add_status.sql, V2.1__fix_index.sql

ALTER TABLE orders ADD COLUMN delivery_status VARCHAR(50) DEFAULT 'PREPARING';
CREATE INDEX idx_orders_delivery ON orders(delivery_status);

15. Zaman Serisi (Time-Series) Veritabanları

IoT sensör verileri, sunucu metrikleri ve finansal loglar gibi sürekli akan verilerin yüksek hızda yazılması ve analiz edilmesi.

Zaman Serisi Doğası & TimescaleDB

Zaman serisi verileri sadece eklenir (Append-Only), güncellenmez. PostgreSQL tabanlı TimescaleDB veya InfluxDB bu veriler için tasarlanmıştır. TimescaleDB, Hypertable adı verilen sanal bir tablo sunar; arka planda verileri zamana göre otomatik olarak küçük parçalara (chunk) böler (Partitioning).

Production Note: Retention & Downsampling Saniyede 10.000 metrik basan bir sistem diski hızla doldurur. Çözüm otomatik veri yaşam döngüsüdür:

Retention Policy: "3 aydan eski ham verileri otomatik sil"
Downsampling: "Geçmiş aylara ait saniyelik verileri tutma, saatlik ortalamasını hesaplayıp (Rollup) onu sakla"

CREATE TABLE sensor_data (

    temperature DOUBLE PRECISION
);

16. Bulut Veritabanı Mimarileri & Connection Pooling (Bağlantı Havuzu)

Modern DBaaS (Veritabanı Servisi) altyapıları ve uygulama ile veritabanı arasındaki darboğazların giderilmesi.

Cloud-Native Mimari (Aurora & Spanner)

AWS Aurora, işlem motoru (Compute) ile depolama motorunu (Storage) fiziksel olarak ayırır. Böylece depolama kendi kendine sınırsız büyürken, okuma kopyaları (Read Replica) milisaniyeler içinde ayağa kalkar. Google Spanner ise atomik saatler (TrueTime API) kullanarak küresel (Global) ölçekte ACID tutarlılığı sunar.

Connection Pooling (Bağlantı Havuzu)

Veritabanına açılan her yeni bağlantı (Connection), TCP el sıkışması ve kimlik doğrulama süreçleri nedeniyle çok maliyetlidir. Her istekte yeni bağlantı açmak (Connection Churn) veritabanını anında çökertir.

DevOps Tip: Pool Konfigürasyonu (HikariCP / PgBouncer) Havuza 10.000 bağlantı koymak performansı artırmaz, aksine işlemci bağlam değişiminden (Context Switch) ötürü kilitler (Starvation).

Altın Formül (PostgreSQL): Connections = ((Core Count * 2) + Etkili Disk (Spindle) Sayısı). Çoğu devasa sistem için 20-50 bağlantı boyutundaki bir havuz optimum performansı sağlar.
hikari_pool.properties 
# Java Spring Boot - HikariCP Optimum Ayarları
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.minimum-idle=5

# Boşta kalan bağlantının atılma süresi
spring.datasource.hikari.idle-timeout=300000 

# Bir isteğin havuzdan bağlantı alabilmek için bekleyeceği maksimum süre
spring.datasource.hikari.connection-timeout=20000

17. Komutlar ve Kısaltma Sözlüğü

Veritabanı dünyasında en sık karşılaşılan kısaltmalar ve anlamları:

Sorgu Dilleri

SQL (Structured Query Language): İlişkisel DB'lerde veri tanımlama, düzenleme ve sorgulama standart dili.

Cypher (CQL): Neo4j'nin grafik yapılarını ASCII sanatıyla ifade eden (node)-[:EDGE]->(node) sorgu dili.

DDL (Data Definition Language): Tablo ve şema komutları (CREATE, ALTER, DROP).

DML (Data Manipulation Language): Veri işleme komutları (SELECT, INSERT, UPDATE, DELETE).

Sistem Mimarileri

DBMS (Database Management System): Veriyi yöneten ara yazılım katmanı (PostgreSQL, MongoDB vb.).

ACID: İlişkisel DB'lerin transaction güvenliği (Atomicity, Consistency, Isolation, Durability).

BASE: NoSQL sistemlerin (Nihai tutarlılık) benimsediği felsefe (Basically Available, Soft-state, Eventually consistent).

TTL (Time To Live): Cache ve NoSQL'de anahtarın süresinin ne zaman dolacağını belirten süre.

CRUD Operasyonları Karşılaştırması

İşlem SQL MongoDB Redis
Create INSERT insertOne SET
Read SELECT find GET
Update UPDATE updateOne SET (üzerine yaz)
Delete DELETE deleteOne DEL

🗄 SQL (PostgreSQL / MySQL)

-- Tablo Oluşturma (DDL)
CREATE TABLE kullanicilar (
    id SERIAL PRIMARY KEY,
    ad VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    olusturulma TIMESTAMP DEFAULT NOW()
);

-- Veri Ekleme (DML)
INSERT INTO kullanicilar (ad, email) VALUES ('Ahmet', 'ahmet@example.com');

-- Aggregate ve Join
SELECT k.ad, COUNT(s.id) as siparis_sayisi
FROM kullanicilar k
LEFT JOIN siparisler s ON s.kullanici_id = k.id
GROUP BY k.id;

-- Transaction
BEGIN;
  UPDATE hesaplar SET bakiye = bakiye - 100 WHERE id = 1;
  UPDATE hesaplar SET bakiye = bakiye + 100 WHERE id = 2;
COMMIT;

// Yeni Doküman Ekleme
db.kullanicilar.insertOne({
    ad: "Fatma", email: "fatma@example.com",
    roller: ["admin", "editor"],
    adres: { sehir: "İstanbul", posta: "34000" }
});

// Filtreli Sorgulama
db.kullanicilar.find({ "adres.sehir": "İstanbul" }).limit(5);

// Aggregation Pipeline
db.kullanicilar.aggregate([
    { $match: { "aktif": true } },
    { $group: { _id: "$adres.sehir", sayi: { $sum: 1 } } }
]);

// Güncelleme
db.kullanicilar.updateOne({ email: "fatma@example.com" }, { $set: { "adres.sehir": "Ankara" } });
