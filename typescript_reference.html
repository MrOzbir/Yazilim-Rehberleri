05 Utility Types Deep Dive

TypeScript'in sunduğu yerleşik Utility Types (Yardımcı Tipler), mevcut tipleri dönüştürmek ve manipüle etmek için güçlü araçlardır.

Pick<T, K> ve Omit<T, K>

Büyük nesne tiplerinden sadece ihtiyacımız olan alanları seçmek (Pick) veya belirli alanları dışlamak (Omit) için kullanılır.

pick-omit.ts 
interface UserProfile {
  id: string;
  username: string;
  email: string;
  avatarUrl: string;
  role: 'admin' | 'user';
}

// Sadece id ve username alanlarını seçiyoruz
type UserPreview = Pick<UserProfile, 'id' | 'username'>;

// Hassas bilgileri (email, role) dışlıyoruz
type PublicUser = Omit<UserProfile, 'email' | 'role'>;

const renderUser = (user: PublicUser) => {
  console.log(user.username, user.avatarUrl);
};
Good Practice: API yanıtlarından veya büyük modellerden DTO (Data Transfer Object) oluştururken Omit veya Pick kullanmak tipleri merkezi bir yerde tutmanızı sağlar.

Partial<T>, Required<T> ve Readonly<T>

Bu tipler bir nesnenin mutability (değiştirilebilirlik) ve opsiyonellik durumlarını topluca manipüle etmeyi sağlar.

Kullanım Senaryoları

  • Partial<T>: Güncelleme (Update) işlemlerinde, tüm alanların opsiyonel olması gerektiğinde.
  • Required<T>: Opsiyonel alanların hepsinin doldurulmasını zorunlu tutmak istediğimiz form validasyonlarında.
  • Readonly<T>: Nesnenin referansının değiştirilmesini engelleyerek immutability (değişmezlik) sağlamak için.
mutability.ts 
interface Todo {
  title: string;
  description?: string;
}

// Bütün alanlar opsiyonel (?) olur
const updateTodo = (todo: Todo, fieldsToUpdate: Partial<Todo>) => {
  return { ...todo, ...fieldsToUpdate };
};

// Error: description artık zorunlu!
const requireAll: Required<Todo> = { title: "Test" }; // Type-Check Error

// Error: Nesne değiştirilemez!
const frozenTodo: Readonly<Todo> = { title: "Freeze" };
frozenTodo.title = "Melt"; // Type-Check Error: Cannot assign to 'title' because it is a read-only property.

Record<K, T> ve Exclude/Extract Küme Operasyonları

Record genellikle dinamik sözlükler (dictionary) veya map yapıları kurmak için kullanılır. Exclude ve Extract ise Union tipler üzerinde küme teorisi işlemleri (fark ve kesişim) yapar.

record-set.ts 
type Role = 'admin' | 'editor' | 'viewer';

// Record ile tüm rollere karşılık gelen yetki listesini mapliyoruz
const rolePermissions: Record<Role, string[]> = {
  admin: ['read', 'write', 'delete'],
  editor: ['read', 'write'],
  viewer: ['read']
};

// Küme İşlemleri
type T0 = Exclude<"a" | "b" | "c", "a">;  // "b" | "c" (Fark)
type T1 = Extract<"a" | "b" | "c", "a" | "f">;  // "a" (Kesişim)

// Pratik Senaryo: Sadece fonksiyon olan property'leri seçme
type FunctionProperties<T> = {
  [K in keyof T]: T[K] extends Function ? K : never;
}[keyof T];

06 Template Literal Types

Template Literal Types, JavaScript'in template string syntax'ını (`...`) tip seviyesine taşır. Metinleri birleştirerek veya manipüle ederek dinamik tipler üretmemizi sağlar.

Şablon Metin Tiplerinin Temelleri

Union tiplerle birlikte kullanıldığında her olası kombinasyon (kartezyen çarpım) için bir tip üretilir.

template-literal.ts 
type World = "world";
type Greeting = `hello ${World}`; // "hello world"

type Color = "red" | "blue";
type Size = "sm" | "lg";
type ClassName = `btn-${Size}-${Color}`; 
// "btn-sm-red" | "btn-sm-blue" | "btn-lg-red" | "btn-lg-blue"
Bad Practice: Çok fazla union tipi template literal ile birleştirmek tip sistemini tıkayabilir ve derleme (compilation) süresini uzatabilir.

API Endpoint ve CSS Property Güvencesi

Dinamik olarak beklenen string yapılarını kurallara bağlamak için idealdir.

api-css.ts 
// CSS padding kuralları: p-4, pt-2, pb-8 vb.
type Direction = "t" | "b" | "l" | "r";
type Spacing = 1 | 2 | 4 | 8;
type PaddingClass = `p${Direction}-${Spacing}` | `p-${Spacing}`;

const pad1: PaddingClass = "pt-4"; // Başarılı
const pad2: PaddingClass = "p-3";  // Type-Check Error: "p-3" is not assignable

// API rotalarını güvenceye alma
type Endpoint = "/users" | "/posts";
type ApiRoute = `/api/v1${Endpoint}`;

const fetchRoute = (route: ApiRoute) => { /* ... */ };
fetchRoute("/api/v1/users"); // Ok
fetchRoute("/api/v2/users"); // Type-Check Error

Mapped Types ve As Cümleleri ile Key Dönüştürme

Capitalize, Uncapitalize, Uppercase, Lowercase yerleşik (intrinsic) tipleriyle objelerin key'lerini dönüştürebiliriz.

key-mapping.ts 
type Getters<Type> = {
  [Property in keyof Type as `get${Capitalize<string & Property>}`]: () => Type[Property]
};

interface Person {
  name: string;
  age: number;
}

type PersonGetters = Getters<Person>;
/* 
Sonuç:
{
  getName: () => string;
  getAge: () => number;
}
*/

07 Classes, Abstract Classes & Interfaces

TypeScript, ECMAScript sınıflarına (classes) erişim belirleyicileri, soyutlamalar ve tip kontrolleri ekleyerek nesne yönelimli (OOP) mimariyi güçlendirir.

Erişim Belirleyiciler (Access Modifiers) ve #private

TS public, private ve protected yapısını sunar. Ancak private JS'e derlendiğinde silinir (Type Erasure). ECMAScript'in yerleşik # private field özelliği ise çalışma zamanında da (runtime) koruma sağlar.

modifiers.ts 
class BankAccount {
  public owner: string;
  private balance: number; // TS seviyesinde gizli (Runtime'da erişilebilir)
  #secretCode: number;     // Gerçek JS runtime gizliliği (ES2015+)

  constructor(owner: string, initialBalance: number) {
    this.owner = owner;
    this.balance = initialBalance;
    this.#secretCode = Math.random();
  }

  protected getBalance() {
    return this.balance; // Alt sınıflardan erişilebilir
  }
}

Abstract Class vs Interface

Birbiriyle sıkça karıştırılan bu iki konseptin kullanım alanları farklıdır.

Yapısal Karşılaştırma

  • Interface: Sadece bir şekil/sözleşme (contract) tanımlar. Runtime'da tamamen silinir. JS çıktısı yoktur. Çoklu implements edilebilir.
  • Abstract Class: Hem tip sözleşmesi sağlar hem de varsayılan davranış/kod (implementation) içerebilir. JS class'ına derlenir. Çoklu extends edilemez.
abstract-vs-interface.ts 
interface Loggable {
  log(message: string): void;
}

abstract class BaseService {
  // Tanımlanmış metot (Varsayılan davranış)
  protected init() {
    console.log("Service Initialized");
  }
  
  // Soyut metot (Alt sınıflar bunu zorunlu doldurmalı)
  abstract process(data: any): boolean;
}

class UserService extends BaseService implements Loggable {
  process(data: any): boolean {
    this.init();
    return true;
  }
  
  log(message: string): void {
    console.log(message);
  }
}
Good Practice: Sadece bir nesnenin şeklini tanımlıyorsanız Interface, eğer alt sınıflara ortak metot/özellik miras bırakmak istiyorsanız Abstract Class kullanın.

Polimorfik "this" Tipi

Akıcı (fluent) API tasarımlarında, metotların geriye dönük kendi sınıflarını (this) döndürmesi this dönüş tipiyle güvenle yapılır.

polymorphic-this.ts 
class QueryBuilder {
  protected query: string = "";
  
  select(fields: string): this {
    this.query += `SELECT ${fields} `;
    return this; // Alt sınıfta çağrılırsa alt sınıfı döner
  }
}

class ExtendedQueryBuilder extends QueryBuilder {
  where(condition: string): this {
    this.query += `WHERE ${condition}`;
    return this;
  }
}

// Zincirleme kullanım (Fluent API)
const q = new ExtendedQueryBuilder()
  .select("*")
  .where("id = 1"); // İki metot da doğru tipte çalışır

08 Advanced Decorators (TS 5.0+)

TypeScript 5.0 ile birlikte Decorators (Dekoratörler) deneysel (experimental) yapıdan çıkıp standart ECMAScript Decorators spesifikasyonuna uygun hale geldi. Dekoratörler, class'ların, metotların veya özelliklerin davranışlarını runtime'da sarmalayarak (wrap) değiştirmeyi sağlar.

Dekoratör Mimarisi ve İmzalar (Signatures)

Yeni standartta dekoratörler, hedef öğeyi ve öğe hakkındaki metadataları (context) parametre olarak alan fonksiyonlardır.

Dekoratör Tipleri

  • Class Decorator: Sınıf tanımını sarmalar, sınıf constructor'ını değiştirebilir.
  • Method Decorator: Bir sınıf metodunu sarmalar. Loglama, yetkilendirme (Auth) veya performans ölçümü (Timing) için çok yaygındır.
  • Property Decorator: Sınıfın bir özelliğini izlemek veya varsayılan değer atamak için kullanılır.

Metot Dekoratörü Örneği: Otomatik Loglama (Logger)

Aşağıdaki örnekte bir metoda yapılan çağrıları, aldığı argümanları ve çalışma süresini otomatik kaydeden bir metot dekoratörü yazıyoruz.

logger-decorator.ts 
// Method Decorator (TS 5.0 Standard)
function loggedMethod<This, Args extends any[], Return>(
  target: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>
) {
  const methodName = String(context.name);

  // Orijinal metodu saran yeni bir metot döndürüyoruz
  return function (this: This, ...args: Args): Return {
    console.log(`[LOG]: ${methodName} metodu çağrıldı. Parametreler:`, args);
    const start = performance.now();
    
    // Orijinal metodu çalıştır
    const result = target.call(this, ...args);
    
    const end = performance.now();
    console.log(`[LOG]: ${methodName} tamamlandı. Süre: ${(end - start).toFixed(2)}ms`);
    
    return result;
  };
}

class Calculator {
  @loggedMethod
  multiply(a: number, b: number): number {
    return a * b;
  }
}

const calc = new Calculator();
calc.multiply(5, 10);
// Çıktı:
// [LOG]: multiply metodu çağrıldı. Parametreler: [5, 10]
// [LOG]: multiply tamamlandı. Süre: 0.15ms
TypeScript 5.0 Öncesi: Eski projelerde dekoratörleri kullanmak için tsconfig.json dosyasında "experimentalDecorators": true açık olmalıydı. Yeni standartta bu zorunluluk kalktı, ancak eski dekoratör framework'leri (Örn: NestJS, Angular) hala experimental modüle ihtiyaç duyabilir.

Çalışma Zamanı (Runtime) Sıralaması

Dekoratörlerin çalışma sırası aşağıdan yukarıya ve içten dışa doğrudur (Matruşka bebekleri gibi). Birden fazla dekoratör eklendiğinde değerlendirme (evaluation) yukarıdan aşağı, çalıştırma (execution) aşağıdan yukarıdır.

09 tsconfig.json Optimizasyonları & Strict Mod

TypeScript derleyicisini (compiler) doğru yapılandırmak, hem geliştirici deneyimi (DX) hem de üretim ortamı güvenliği için kritiktir. tsconfig.json dosyasındaki ayarlar, projenizin tip gücünü belirler.

"strict": true ve Alt Kuralları

Projenizde "strict": true bayrağını açmak, TypeScript'in tam potansiyelini kullanmanın ilk şartıdır. Bu bayrak aslında birden fazla sıkı kuralı aynı anda aktifleştirir.

Strict Mod Alt Kuralları

  • noImplicitAny: Tiplerin açıkça belirtilmediği durumlarda derleyicinin "any" atamasına izin vermez.
  • strictNullChecks: null ve undefined değerlerinin diğer tiplerin alt kümesi olmasını engeller (Billion dollar mistake'i önler).
  • strictFunctionTypes: Fonksiyon parametrelerinin "bivariant" yerine "contravariant" olarak sıkı kontrol edilmesini sağlar.
Production Tip: Mevcut büyük bir projeye TS entegre ediyorsanız, strict modları kademeli olarak (önce strictNullChecks, sonra noImplicitAny) açarak refactoring yükünü dağıtabilirsiniz.

Derleme Performansı Ayarları

Devasa monorepo projelerinde derleme (build) sürelerini kısaltmak için özel ayarlar yapılandırılmalıdır.

tsconfig.json 
{
  "compilerOptions": {
    "target": "ES2022",     // Modern motorlar için daha az polyfill üretir
    "module": "ESNext",     // Bundler'lar (Vite, Webpack) için Tree Shaking sağlar
    "incremental": true,    // .tsbuildinfo dosyası ile sadece değişenleri derler (Hız x10)
    "skipLibCheck": true    // node_modules içindeki devasa .d.ts dosyalarını kontrol etmeyi atlar
  }
}

Path Mapping (Temiz Import Yolları)

Büyük projelerde ../../../../components/Button gibi "relative" yollardan kurtulmak için paths ayarı kullanılır.

tsconfig.paths.json 
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/components/*": ["src/components/*"],
      "@/utils/*": ["src/utils/*"],
      "@/api/*": ["src/api/*"]
    }
  }
}
Compiler Note: TypeScript derleyicisi path mapping'i JavaScript dosyalarına (runtime paths) çevirmez! Bunu bundler'ınıza (Örn: Webpack'te resolve.alias, Vite'ta vite-tsconfig-paths) ayrıca öğretmeniz gerekir.

10 Asenkron Tipler & Promises

TypeScript, asenkron JavaScript konseptlerini (Promises, async/await, async generators) yönetmek için özel yerleşik tipler ve güçlü bir çıkarım mekanizması sunar.

Promise<T> Jenerik Yapısı

Asenkron bir fonksiyon her zaman bir Promise döner. Dönüş tipini kontrol etmek, hatasız zincirleme (chaining) yapabilmek için kritiktir.

async-types.ts 
interface UserData {
  id: string;
  name: string;
}

// Dönüş tipi explicit olarak Promise<UserData> belirlendi
async function fetchUser(id: string): Promise<UserData> {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) throw new Error("Ağ hatası");
  return response.json(); // Implicit olarak any dönebilir, Promise<UserData> bunu korur
}

Awaited<T> ile İç İçe Promiseleri Düzleştirme (Unwrapping)

Awaited yardımcı tipi, bir Promise'in çözüleceği (resolve olacağı) en son saf (raw) değeri tip olarak almanızı sağlar. İç içe (nested) Promise'leri bile tek seferde düzleştirir.

awaited-type.ts 
type NestedPromise = Promise<Promise<string>>;

// T1 = string olur
type T1 = Awaited<NestedPromise>; 

// Pratik Kullanım: Bir fonksiyonun çözülmüş dönüş tipini alma
type FetchUserReturnType = ReturnType<typeof fetchUser>; // Promise<UserData>
type UnwrappedUserData = Awaited<ReturnType<typeof fetchUser>>; // UserData
Good Practice: Harici bir kütüphaneden gelen asenkron bir fonksiyonun dönüş değerini lokal bir tipte saklamak isterseniz her zaman Awaited<ReturnType<typeof ...>> kullanın.

Async Generators (Streams) Tiplenmesi

Veri akışlarında (örneğin WebSockets veya Pagination streamleri) AsyncGenerator tipi kullanılır.

async-generator.ts 
// AsyncGenerator<VeriTipi, ReturnTipi, NextParametresi>
async function* fetchAllPages(): AsyncGenerator<string[], void, unknown> {
  let page = 1;
  while (true) {
    const data = await fetch(`/api/items?page=${page}`).then(r => r.json());
    if (data.length === 0) break;
    yield data;
    page++;
  }
}

// Kullanımı
(async () => {
  for await (const chunk of fetchAllPages()) {
    console.log(chunk); // chunk tipi: string[]
  }
})();

11 Runtime (Çalışma Zamanı) Tip Doğrulama

TypeScript mükemmel bir statik analiz aracıdır, ancak çalışma zamanında (runtime) tip garantisi sunmaz. Güvenli kod için statik tipleri runtime doğrulaması ile birleştirmek şarttır.

Type Erasure ve Güvenlik Açığı

Type Erasure (Tip Silinmesi), TS kodunuz JS'ye çevrildiğinde tüm tip (interface, type) bilgilerinin kaybolmasıdır. Ağdan veya kullanıcıdan gelen bozuk bir veri, TS tarafından yakalanamaz.

Production Risk: const user = await response.json() as User; gibi bir Type Assertion kullandığınızda, API size sayılar yerine string dönse bile sistem çökmeyip sessizce bozulmaya (silent bug) devam edebilir.

Çözüm: Şema Tabanlı Doğrulama (Schema Validation)

Veriyi doğrulamak ve bu doğrulamadan bir TypeScript tipi türetmek için Zod, Yup veya TypeBox gibi kütüphaneler kullanılır. Buna endüstride "Parse, don't validate" yaklaşımı denir.

"Parse, don't validate" Prensibi

Veriyi sadece "doğru mu?" diye kontrol etmek yerine, veriyi güvenli olduğunu bildiğiniz kesin bir yapıya parse edip o güvenli objeyi dönersiniz.

zod-validation.ts 
import { z } from "zod";

// 1. Runtime Şemasını Tanımla
const UserSchema = z.object({
  id: z.string().uuid(),
  username: z.string().min(3).max(20),
  email: z.string().email(),
  isActive: z.boolean().default(true)
});

// 2. Statik Tipi Şemadan Türet (Dry Prensibi - Tipleri iki kere yazma!)
type User = z.infer<typeof UserSchema>;

// 3. Güvenli API Fonksiyonu
async function fetchSafeUser(userId: string): Promise<User> {
  const response = await fetch(`/api/users/${userId}`);
  const rawData = await response.json();
  
  // Eğer veri şemaya uymazsa runtime hatası (ZodError) fırlatır
  // Uyarsa güvenli ve tam tiplemeli objeyi döner
  const safeData = UserSchema.parse(rawData);
  
  return safeData;
}
Architecture Tip: Zod gibi kütüphaneleri dışarıya açık tüm sistem sınırlarına (API Payload'ları, Form verileri, LocalStorage okumaları, Env değişkenleri) yerleştirin.

12 Monorepo, Deklarasyon Dosyaları (.d.ts) ve Dağıtım

TypeScript projeleri büyüdükçe kütüphane dağıtımı, saf JS paketlerine tip yazımı ve büyük mimarilerin yapılandırılması konuları devreye girer.

.d.ts (Declaration Files) Dosyaları ve "declare"

Deklarasyon dosyaları, çalışma zamanında (runtime) kod içermeyen, sadece derleyiciye "Burada bir şeyler var ve tipleri bunlardır" demeye yarayan saf tip dosyalarıdır.

global.d.ts 
// Tip desteği olmayan eski bir jQuery kütüphanesine tip yazma
declare module "legacy-jquery" {
  export function $(selector: string): any;
  export const version: string;
}

// Global (Window) nesnesine özel değişken ekleme
declare global {
  interface Window {
    __ANALYTICS_ID__: string;
  }
}
// global.d.ts dosyasının bir modül olması için boş export
export {};

Module Resolution (Modül Çözümleme)

Derleyicinin bir import gördüğünde dosyayı nasıl bulacağını belirler. tsconfig.json dosyasındaki moduleResolution ayarı hayati önem taşır.

Modern Çözümleme Stratejileri

  • NodeNext / Node16: Projenizi doğrudan Node.js'te (Native ESM) çalıştıracaksanız veya kütüphane yayınlıyorsanız kullanılır. import { Foo } from "./foo.js"; gibi uzantı belirtilmesini zorunlu kılar.
  • Bundler: Vite, esbuild veya Webpack gibi paketleyiciler kullanıyorsanız en ideal ve güncel ayardır. Paketlerin package.json'daki "exports" kurallarını doğru okur.

Monorepo ve Project References (composite)

Devasa (100k+ satır) projelerde, tüm projeyi tek seferde derlemek hafıza sorunlarına ve uzun sürelere neden olur. Project References ile proje alt paketlere bölünür.

packages/backend/tsconfig.json 
{
  "compilerOptions": {
    "composite": true,       // Referanslanabilir bir paket olduğunu belirtir
    "declaration": true,     // Ortak projelerin tipleri görebilmesi için .d.ts üretir
    "outDir": "./dist"
  },
  "references": [
    // Ortak (shared) kütüphaneye bağımlılığı belirtir
    { "path": "../shared" }
  ]
}
Compiler Note: Project References kurulan bir monorepo'da, projeyi derlemek için tsc komutu yerine tsc -b (build mod) kullanılmalıdır. Bu mod sadece değişen paketleri (incremental) sırayla derler.
