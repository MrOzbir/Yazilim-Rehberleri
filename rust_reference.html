Rust Reference

01. Bellek Yönetimi: Ownership (Mülkiyet) Sistemi

Rust'ın bellek yönetme felsefesi geleneksel dillerden ayrılır. Çöp toplayıcı (Garbage Collector) veya manuel free() çağrıları yerine, sahiplik kuralları ve RAII (Resource Acquisition Is Initialization) prensibine dayanır. Veri kapsam (scope) dışına çıktığı an bellek otomatik olarak temizlenir.

Üç Temel Ownership Kuralı

  • Rust'taki her değerin bir sahibi (owner) vardır.
  • Aynı anda sadece tek bir sahip olabilir.
  • Sahip kapsam (scope) dışına çıktığında, değer silinir (dropped).

Move, Copy ve Clone Semantikleri

Stack üzerinde yaşayan basit veriler kopyalanır (Copy), ancak heap üzerinde yaşayan veriler (örneğin String) varsayılan olarak taşınır (Move). Heap verisini derin kopyalamak istiyorsanız Clone kullanmalısınız.

Compile Error: Use of moved value Taşınmış (moved) bir veriyi tekrar kullanmaya çalıştığınızda derleyici anında hata verir.
ownership.rs 
fn main() {
    // 1. Copy Semantiği (Stack)
    let x = 5;
    let y = x; // x kopyalandı, ikisi de geçerli.

    // 2. Move Semantiği (Heap)
    let s1 = String::from("Rust");
    let s2 = s1; // s1'in sahipliği s2'ye taşındı (moved)
    
    // println!("{}", s1); // HATA! s1 artık geçerli değil.

    // 3. Clone Semantiği
    let s3 = s2.clone(); // Derin kopya (Deep copy)
    println!("s2: {}, s3: {}", s2, s3); // İkisi de geçerli
}

02. Ödünç Alma (Borrowing) & Borrow Checker

Her değerin sahipliğini transfer etmek yorucu olabilir. Referanslar (&) aracılığıyla verilere geçici erişim hakkı sağlamaya Borrowing (Ödünç Alma) denir. Derleyicinin kalbi olan Borrow Checker, bu referansların kurallara uygunluğunu denetler.

Kutsal Borrow Checker Kuralları

Herhangi bir veri için aşağıdaki iki durumdan sadece biri geçerli olabilir:

  • Sınırsız sayıda salt-okunur (immutable) referans (&T).
  • Sadece bir adet değiştirilebilir (mutable) referans (&mut T).
Aliasing + Mutation = Hata Rust, aynı anda birden fazla okuyucuya izin verirken, yazıcı varken kimsenin okumasına veya başka bir yazıcının olmasına izin vermez. Bu mekanizma Data Race (Veri Yarışı) durumlarını tamamen derleme zamanında yok eder.
borrowing.rs 
fn main() {
    let mut data = String::from("Sistem Programlama");

    // Salt-okunur ödünç almalar (Sorunsuz)
    let r1 = &data;
    let r2 = &data;
    println!("Okunanlar: {} ve {}", r1, r2);
    // r1 ve r2'nin kapsamı burada biter

    // Değiştirilebilir ödünç alma
    let r3 = &mut data;
    r3.push_str(" (Rust)");
    
    // let r4 = &data; // HATA! r3 aktifken okuma yapılamaz.
    println!("Güncel: {}", r3);
}

03. Yaşam Süreleri (Lifetimes)

Borrow Checker'ın en yakın arkadaşı Lifetimes mekanizmasıdır. Bir referansın işaret ettiği verinin bellekte ne kadar süreyle geçerli kalacağını belirler ve Dangling Pointer (Boşta Kalan Gösterici) hatalarını önler.

Lifetime Elision ve Explicit Syntax

Çoğu zaman derleyici örtülü ömür kuralları (Lifetime Elision) sayesinde referans ömürlerini kendi tahmin eder. Ancak tahmin edemediği durumlarda açık (explicit) olarak <'a> sözdizimi ile belirtilmesi gerekir.

Dangling Reference Bir veri kapsam dışına çıkıp yok edildiğinde, ona işaret eden bir referansın hala yaşamasına Rust izin vermez.
lifetimes.rs 
// 'a: Her iki parametrenin ve dönüş değerinin ömrünü birbirine bağlar
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() {
        x
    } else {
        y
    }
}

fn main() {
    let string1 = String::from("uzun metin");
    let result;
    {
        let string2 = String::from("kısa");
        // result = longest(string1.as_str(), string2.as_str()); 
        // HATA! string2 kapsam dışına çıkacağı için result dangling olur.
    }
    
    // 'static ömrü: Programın sonuna kadar yaşar
    let s: &'static str = "Ben hep buradayım.";
}

04. Hata Yönetimi: Kayıpsız Güvenlik

Rust'ta null değeri veya try/catch bloklu geleneksel Exceptions (İstisnalar) yoktur. Bunun yerine güçlü enum yapıları ve pattern matching vardır.

Panics vs. Result/Option

  • Kurtarılamaz Hatalar (Panic): panic!("Hata!") çağrılır. İşletim sistemi programı sonlandırır.
  • Kurtarılabilir Hatalar (Result/Option): Hata durumu bir değer olarak döner, derleyici sizi onu işlemeye zorlar.
Soru İşareti (?) Operatörü Bir fonksiyondan Result/Option dönerken hata (Err/None) geldiyse işlemi anında durdurup hatayı bir üst kapsama fırlatmak (Error Propagation) için ? operatörü en iyi pratiktir.
error_handling.rs 
use std::fs::File;
use std::io::{self, Read};

// Kurtarılabilir Hata: Result<String, io::Error> Döner
fn read_username_from_file() -> Result<String, io::Error> {
    let mut username = String::new();
    
    // ? operatörü Err ise anında fonksiyondan çıkar ve hatayı döner
    let mut file = File::open("hello.txt")?;
    file.read_to_string(&mut username)?;
    
    Ok(username) // Başarılı sonuç Ok() içine sarılır
}

fn main() {
    // Pattern matching ile unwrap pratiği
    match read_username_from_file() {
        Ok(name) => println!("Kullanıcı adı: {}", name),
        Err(e) => println!("Dosya okuma hatası: {}", e),
    }
}

05. Akıllı Göstericiler (Smart Pointers)

Referanslar (&) sadece bellek adresi işaret ederken, Akıllı Göstericiler (Smart Pointers) metadata ve ekstra yeteneklere (örn. reference counting) sahiptir ve Drop trait ile belleği otomatik temizlerler.

Box<T>: Heap Tahsisi

Veriyi Stack yerine Heap bellekte tutmak için kullanılır. Özellikle derleme zamanında boyutu bilinmeyen (örn. Recursive Types) yapıları sarmalamak için idealdir.

box_example.rs 
// Recursive veri yapısı örneği (Linked List benzeri)
enum List {
    Cons(i32, Box<List>),
    Nil,
}

use crate::List::{Cons, Nil};

fn main() {
    // Heap üzerinde saklanan iç içe yapı
    let list = Cons(1, Box::new(Cons(2, Box::new(Nil))));
}

Rc<T> ve Arc<T>: Çoklu Sahiplik

Bazen bir verinin birden fazla sahibi olması gerekir. Rc (Reference Counted), işaretçi sayısını sayarak veri kullanımda olduğu sürece heap'te tutar. Çok thread'li ortamlar için atomik versiyonu olan Arc (Atomic Reference Counted) kullanılır.

Compile Error: Rc Thread-Safe Değildir! Rc<T>'yi başka bir thread'e taşımaya çalışırsanız derleyici "Rc<T> cannot be sent between threads safely" hatası verir.

RefCell<T>: İçsel Değiştirilebilirlik (Interior Mutability)

Değişmez (immutable) bir referans üzerinden veriyi değiştirmeye olanak tanır. Borrow Checker kurallarını derleme (compile) zamanından, çalışma (runtime) zamanına kaydırır.

refcell.rs 
use std::cell::RefCell;

fn main() {
    let data = RefCell::new(5);
    
    // Immutable değişken üzerinden mutable işlem yapma
    *data.borrow_mut() += 10;
    
    println!("Sonuç: {}", data.borrow()); // Çıktı: 15
}

06. Concurrency (Eşzamanlılık) & Send/Sync

Rust'ın Korkusuz Eşzamanlılık (Fearless Concurrency) yaklaşımı, Data Race gibi klasik bug'ları tip sistemi ile derleme aşamasında tamamen engeller.

Send ve Sync Marker Protokolleri

  • Send: Bir veri tipinin sahipliği (ownership) başka bir thread'e güvenle aktarılabilir mi? (Çoğu tip Send'dir, ancak Rc<T> değildir.)
  • Sync: Bir veri tipi birden fazla thread tarafından referans ile (&T) güvenle okunabilir mi? (Bir tip Sync ise, &T Send'dir.)

Veri Paylaşım Kalıpları: Arc<Mutex<T>>

Birden fazla thread'in aynı veriyi güvenle değiştirmesi için Shared State kullanılır. Arc çoklu referans sayımını sağlarken, Mutex (Mutual Exclusion) veriyi kilitleyerek Veri Yarışını (Data Race) engeller.

Mutex Poisoning Bir thread kilidi (lock) elinde tutarken panic olursa, Mutex zehirlenir (poisoned). Rust, lock().unwrap() ile sizi bu durumu yönetmeye zorlar.
concurrency.rs 
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // Hem thread-safe referans sayacı (Arc) hem de kilit (Mutex)
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter_clone = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            // Kilidi al ve veriyi değiştir (RAII: Scope sonunda kilit otomatik açılır)
            let mut num = counter_clone.lock().unwrap();
            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Sonuç: {}", *counter.lock().unwrap()); // Çıktı: 10
}

07. Traits, Generics & Polimorfizm

Object-Oriented dillerdeki arayüzlere (Interfaces) benzeyen Traits, Rust'ta davranışları (behavior) tanımlar ve Polimorfizm sağlar.

Statik Dağıtım vs Dinamik Dağıtım

  • Statik Dağıtım (impl Trait): Derleme zamanında Monomorphization yapılarak her tip için özel fonksiyon üretilir. Sıfır maliyetlidir (Zero-cost abstraction) ama binary boyutunu artırır.
  • Dinamik Dağıtım (dyn Trait): Çalışma zamanında (runtime) vtable mekanizması ile çözümlenir. Pointer (örn: Box<dyn Trait>) gerektirir, binary küçüktür ama ufak bir performans maliyeti vardır.

Trait Bounds & Generics

Jenerik fonksiyonları (Generics) belirli yeteneklere sahip tiplerle sınırlandırmak (kısıtlamak) için kullanılır.

traits.rs 
use std::fmt::Display;

// where sentaksı ile temiz Trait Bounds kullanımı
fn notify_and_print<T, U>(item: &T, data: &U) 
    where T: Display + Clone,
          U: Clone + std::fmt::Debug
{
    println!("Bildirim: {}", item);
    println!("Data: {:?}", data);
}

08. Unsafe Rust & FFI (Foreign Function Interface)

Rust'ın garanti ettiği bellek güvenliği her durumda yeterli olmayabilir. İşletim sistemiyle, C kütüphaneleriyle veya gömülü donanımlarla konuşurken Unsafe Rust kullanılır.

Unsafe Rust'ın 5 Süper Gücü

Derleyicinin emniyet kemerini çözdüğü yerler:

  1. Ham göstericilerin (Raw Pointers: *const T, *mut T) dereference edilmesi.
  2. Unsafe fonksiyonların ve metotların çağrılması.
  3. Mutable statik (global) değişkenlerin değiştirilmesi.
  4. Unsafe trait'lerin implemente edilmesi.
  5. union alanlarına erişim sağlanması.
Safe Wrapper Deseni Hiçbir zaman doğrudan unsafe fonksiyonları kullanıcıya açmayın. Unsafe C kodlarını güvenli (Safe) bir Rust API'si (Wrapper) içine sararak bellek güvenliği ihlalini sınırlandırın.

FFI (C Kütüphanelerini Bağlama)

ffi.rs 
// C dilinin abs() fonksiyonunu bağlıyoruz
extern "C" {
    fn abs(input: i32) -> i32;
}

// Güvenli (Safe) Wrapper
pub fn safe_abs(input: i32) -> i32 {
    // Unsafe bloğu sadece C sınırında (boundary) kullanıyoruz
    unsafe {
        abs(input)
    }
}

// C uyumlu (C-compatible) Struct (Memory Layout)
#[repr(C)]
pub struct FfiStruct {
    pub x: f32,
    pub y: f32,
}

fn main() {
    let result = safe_abs(-42);
    println!("Mutlak değer: {}", result); // 42
}

09. İleri Düzey Tür Sistemleri & Lifetimes Kalıpları

Rust'ın tip sistemi, derleme aşamasında en karmaşık kuralları bile ifade etmenize olanak tanır. State-machine'leri sadece tip sistemiyle doğrulamak bile mümkündür.

PhantomData ve Tip Sistemi Hileleri

Çalışma zamanında (runtime) bellekte 0 byte yer kaplayan PhantomData<T>, sadece derleyiciye (statik analizör) "Ben T tipinde veya lifetime'ında bir veri taşıyor gibi davranıyorum" mesajı vermek için kullanılır.

Production Tip: State Typestate Pattern Sistem durumlarını (örneğin "Açık Kapı" ve "Kapalı Kapı") Struct parametreleri olarak kodlayıp, geçersiz durum geçişlerini derleme anında durdurmak için PhantomData kullanılır.
phantom.rs 
use std::marker::PhantomData;

// State tipleri
struct Draft;
struct Published;

// Makale yapısı o anki state'i tip sisteminde tutar
struct Article<State> {
    content: String,
    state: PhantomData<State>,
}

impl Article<Draft> {
    // Sadece Draft durumundayken publish yapılabilir
    fn publish(self) -> Article<Published> {
        Article {
            content: self.content,
            state: PhantomData,
        }
    }
}

Lifetime Bounds & Blanket Implementations

T: 'a sözdizimi, "T içindeki tüm referanslar en az 'a kadar yaşamalı" anlamına gelir. Blanket Implementations ise belirli bir koşulu sağlayan her tipe toplu olarak trait kazandırır (Örn: "Display implemente eden her şeye ToString kazandır").

10. Makrolar & Metaprogramlama (Macros)

Rust'ta "Makrolar kodu yazan koddur" (Metaprogramming). Fonksiyonlardan farklı olarak, makrolar parametre sayısında esnektir ve kodu AST seviyesinde değiştirir.

Declarative Macros (Bildirimsel Makrolar)

macro_rules! kullanılarak yazılır. Match pattern'leri (expr, ident, tt vb.) ile token ağaçları işlenir.

declarative.rs 
macro_rules! create_hashmap {
    ( $( $key:expr => $val:expr ),* ) => {
        {
            let mut map = std::collections::HashMap::new();
            $(
                map.insert($key, $val);
            )*
            map
        }
    };
}

fn main() {
    let my_map = create_hashmap!(1 => "Bir", 2 => "İki");
}

Procedural Macros (Süreçsel Makrolar)

Procedural makrolar, Rust kodunu bir TokenStream olarak alıp, derleme sırasında analiz eder ve yeni bir TokenStream üretir. En popüler kullanım alanları #[derive(Serialize)] veya #[tokio::main] gibi yapılardır. Bu işlem genellikle syn ve quote kütüphaneleriyle birlikte yapılır.

11. Profiling, Güvenli Paketleme & Cargo Optimizasyonları

Geliştirme süreci bittiğinde projeyi Production (Üretim) aşamasına hazırlamak için derleyici flag'leri ve kod kalite araçları büyük rol oynar.

Cargo.toml Release Profil Optimizasyonları

Rust varsayılan Release modunda bile bazı optimizasyonları derleme süresini kısaltmak için kapalı tutar. Boyutu küçültmek ve hızı maksimize etmek için bu flag'ler kullanılır.

Performance Note: LTO ve Codegen Units LTO (Link Time Optimization), projeyi tek bir birim olarak ele alıp ölü kodları (dead code) temizler ve performansı %10-20 artırır. codegen-units = 1 ise derlemeyi yavaşlatsa da çalışma anı performansını iyileştirir.
Cargo.toml 
[profile.release]
opt-level = 3        # Maksimum hız optimizasyonu (default)
lto = "fat"          # Link Time Optimization: Bütün kod analiz edilir
codegen-units = 1    # Derleme ünitelerini tek parça yap (daha yavaş derlenir, hızlı çalışır)
panic = "abort"      # Panik anında stack unwinding yapma, direkt çıkış yap (binary'yi küçültür)
strip = true         # Symbol'leri kaldır (binary boyutunu aşırı küçültür)

Kod Kalitesi ve Güvenlik Süreçleri

  • Clippy: Rust'ın resmi linter'ı. cargo clippy komutuyla daha idiomatic (Rust felsefesine uygun) kod yazmanızı önerir.
  • Cargo Audit: cargo audit komutu kullanılarak `Cargo.lock` dosyanızdaki tüm bağımlılıkların bilinen güvenlik açıklarına karşı taranması sağlanır.
  • Criterion: Mikro-benchmark yazarak iki farklı algoritma implementasyonunun (örn: HashMap vs BTreeMap) performans ölçümleri için kullanılır.

12. Async Rust: Future, Tokio Runtime & Event Loop

Modern sistem programlamada I/O beklemeleri sırasında thread'leri bloklamadan milyonlarca isteği eşzamanlı işleyebilmek için Async Rust kullanılır. Rust, JS veya Go'dan farklı olarak Asenkron motoru dilin çekirdeğinde sunmaz; Future trait'i ile sözleşme yapar ve işleyişi Tokio gibi bağımsız Runtime kütüphanelerine bırakır.

Future Traiti ve Lazy Mekanizması

Rust'ta asenkron bloklar Lazy'dir (Tembel). Bir async fn çağırdığınızda fonksiyon çalışmaz, sadece bir Future objesi döner. İşlemin ilerlemesi için bir Executor'ın ona .await diyerek poll() yapması gerekir.

Tokio Runtime ve Eşzamanlı Görevler (Tasks)

Tokio, Work-Stealing algoritmasına sahip çok thread'li (multi-threaded) bir event-loop sunar. tokio::spawn ile aynı thread havuzu içinde binlerce hafif görev (green-thread/task) başlatılabilir.

Production Tip: Select Makrosu ile Timeout Asenkron I/O işlemlerinde bir görevin sonsuza kadar askıda kalmasını önlemek için tokio::select! ile birden çok future aynı anda bekletilir. İlk biten kazanır.
async_main.rs 
use tokio::time::{sleep, Duration};

async fn fetch_data() -> String {
    sleep(Duration::from_secs(2)).await; // Non-blocking bekleme
    "API Verisi Alındı".to_string()
}

#[tokio::main] // Tokio event-loop'u başlatır
async fn main() {
    println!("İstek gönderiliyor...");

    // select! makrosu: Race condition konsepti
    tokio::select! {
        res = fetch_data() => {
            println!("Başarılı: {}", res);
        }
        _ = sleep(Duration::from_secs(1)) => {
            // Eğer fetch_data 1 saniyeyi geçerse bu blok çalışır
            println!("Hata: İstek Zaman Aşımına Uğradı! (Timeout)");
        }
    }
}
