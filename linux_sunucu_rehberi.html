Bölüm 01

Temel Linux Mimarisi, Kullanıcılar ve İleri Seviye SSH Hardening

1.1 FHS ve Gelişmiş Dosya İzinleri

Orta Seviye

Standart Okuma/Yazma/Çalıştırma (rwx) yetkilerinin yanı sıra, sistem güvenliğini sağlamak için SUID, SGID ve Sticky Bit gibi özel izin yapılarını anlamak elzemdir.

  • SUID (Set User ID): Bir dosyanın (örn. /usr/bin/passwd), dosyayı çalıştıran kullanıcının yetkileriyle değil, dosya sahibinin (root) yetkileriyle çalışmasını sağlar.
  • SGID (Set Group ID): Dizinlere uygulandığında, o dizin içinde oluşturulan dosyalar o dizinin grubunu miras alır. (Ortak çalışma alanları için).
  • Sticky Bit: Sadece dosyanın sahibinin veya root'un o dosyayı silebilmesini sağlar (örn. /tmp dizini).
bash
# Klasik chmod (Sahip: 7, Grup: 5, Diğerleri: 5)
root@server:~# chmod 755 /var/www/html

# SUID Ayarlamak (Sembolik: u+s, Nümerik: 4000)
root@server:~# chmod u+s /opt/scripts/special_script.sh

# Ortak paylaşımlı dizin için SGID Ayarlamak (Sembolik: g+s, Nümerik: 2000)
root@server:~# chmod g+s /var/shared_folder

# Sticky Bit Ayarlamak (Sembolik: +t, Nümerik: 1000)
root@server:~# chmod +t /var/public_uploads

1.2 Sudoers Manipülasyonu (visudo)

İleri Seviye

Her kullanıcıyı sudo grubuna eklemek büyük bir güvenlik açığıdır. Belirli kullanıcılara sadece belirli komutları root olarak çalıştırma yetkisi vermek gerekir. Bu işlem sadece visudo komutu ile yapılmalıdır; dosyayı nano /etc/sudoers ile doğrudan düzenlemek syntax hatasında sistem erişimini kaybetmenize yol açabilir.

/etc/sudoers (visudo üzerinden)
# Geliştirici sadece Nginx servisini yeniden başlatabilsin (şifresiz)
developer ALL=(root) NOPASSWD: /bin/systemctl restart nginx

# DevOps grubu tüm komutları şifresiz çalıştırabilsin
%devops ALL=(ALL:ALL) NOPASSWD: ALL

# Belirli bir komut dosyasını (script) çalıştırma izni
monitor_user ALL=(root) /opt/scripts/health_check.sh

1.3 SSH Hardening Deep Dive

Master Seviye

Sadece Port değiştirmek ve Password Authentication kapatmak yeterli değildir. SSH servisini daha da daraltmak gerekir.

/etc/ssh/sshd_config
# Temel Güvenlik
Port 2222
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes

# İleri Seviye Daraltma (Hardening)
AllowUsers devops admin          # Sadece bu kullanıcılar SSH yapabilir (Kritik!)
MaxAuthTries 3                   # 3 yanlış denemede bağlantıyı kes
ClientAliveInterval 300          # 5 dakika işlem yapılmazsa oturumu düşür
ClientAliveCountMax 2            # Cevap vermeyen istemciyi 2. denemede at
PermitEmptyPasswords no          # Boş şifrelere kesinlikle izin verme
X11Forwarding no                 # GUI uygulamalarının iletilmesini engelle
AllowTcpForwarding no            # SSH Tünellemeyi engelle (Gerekmiyorsa)

# Ayarları test et (syntax hatası var mı?) ve servisi yeniden başlat
root@server:~# sshd -t
root@server:~# systemctl restart sshd
Bölüm 02

Ağ Yönetimi, DNS ve Gelişmiş Güvenlik Duvarı

2.1 Netplan ile Statik IP ve DNS

Orta Seviye

Ubuntu ve modern Linux dağıtımlarında ağ yönetimi /etc/network/interfaces yerine Netplan üzerinden yapılmaktadır.

/etc/netplan/01-netcfg.yaml
network:
  version: 2
  renderer: networkd
  ethernets:
    eth0:
      dhcp4: no
      addresses:
        - 192.168.1.100/24
      routes:
        - to: default
          via: 192.168.1.1
      nameservers:
        addresses:
          - 1.1.1.1
          - 8.8.8.8
        search: [mydomain.local]
Uygulamak için: sudo netplan try (Hata yaparsanız 120 saniye içinde eski ayara döner), memnunsanız sudo netplan apply.

2.2 UFW Rate Limiting ve İptables Mantığı

İleri Seviye

UFW, aslında arka planda Linux çekirdeğinin iptables / netfilter yapısını kullanan bir arayüzdür. Doğrudan UFW üzerinden "Hız Sınırlandırma (Rate Limiting)" uygulayarak kaba kuvvet saldırılarını fail2ban olmadan da yavaşlatabilirsiniz.

bash
# SSH Portu için Rate Limiting uygula 
# (Aynı IP'den 30 saniye içinde 6'dan fazla bağlantı gelirse banlar)
root@server:~# ufw limit 2222/tcp

# Belirli bir IP bloğuna (Subnet) tam erişim
root@server:~# ufw allow from 10.0.0.0/8

# Giden trafiği engelle ve sadece belirli portlara izin ver (Sunucu hacklense bile dışarı veri kaçıramaz)
root@server:~# ufw default deny outgoing
root@server:~# ufw allow out 80/tcp
root@server:~# ufw allow out 443/tcp
root@server:~# ufw allow out 53/udp  # DNS Sorguları için şart!

2.3 Fail2Ban İleri Konfigürasyon ve Log Okuma

İleri Seviye

Fail2ban'in en güçlü yanı sadece SSH'ı değil, Nginx/Apache loglarını da okuyarak web tabanlı taramaları (botları) engelleyebilmesidir.

/etc/fail2ban/jail.local
[DEFAULT]
bantime = 1h          # Varsayılan ban süresi
findtime = 10m        # Denemelerin sayıldığı zaman aralığı
maxretry = 5          # Maksimum deneme

[sshd]
enabled = true
port = 2222
maxretry = 3          # SSH için özel olarak düşürdük

# Nginx 404 (Not Found) tarayan botları engelle
[nginx-botsearch]
enabled = true
port     = http,https
logpath  = %(nginx_error_log)s
maxretry = 2          # 2 hatalı url taramasında banla!
Banlanmış IP'leri Görmek: fail2ban-client status sshd
Bir IP'nin banını kaldırmak (Unban): fail2ban-client set sshd unbanip 1.2.3.4
Bölüm 03

Modern Web Sunucusu ve Proxy Mimarisi (Nginx)

3.1 Yük Dengeleme (Load Balancing) ve Upstream Mimarisi

Master Seviye

Arka planda çalışan birden fazla Node.js veya Python sürecine (process) trafiği paylaştırmak için upstream bloğu kullanılır. Bu sayede High-Availability (Yüksek Erişilebilirlik) sağlanır.

/etc/nginx/nginx.conf veya sites-available/api
# Sunucu havuzunu tanımla
upstream backend_api {
    # Varsayılan algoritma Round-Robin'dir (Sırayla dağıtır)
    # least_conn; eklenirse en az bağlantısı olana yönlendirir
    # ip_hash; eklenirse aynı IP hep aynı sunucuya düşer (Session koruma)
    
    server 127.0.0.1:3000 weight=3; # Bu sunucuya 3 kat daha fazla trafik ver
    server 127.0.0.1:3001;
    server 127.0.0.1:3002 backup;   # Diğerleri çökerse devreye gir
}

server {
    listen 80;
    server_name api.domain.com;

    location / {
        proxy_pass http://backend_api; # Havuza yönlendir
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

3.2 Güvenlik Başlıkları (Security Headers) ve Mikro-Önbellekleme

İleri Seviye

Nginx üzerinden XSS, Clickjacking gibi saldırıları engellemek için HTTP response header'larına müdahale edilmelidir. Ayrıca anlık trafik patlamalarında backend'i korumak için microcaching uygulanabilir.

Bilgi: add_header Strict-Transport-Security (HSTS) tarayıcıya sitenin "sadece ve her zaman HTTPS üzerinden çalışması gerektiğini" söyler.
Nginx Security & Cache Config
# Cache Yolu Tanımlama (http bloğu içine)
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m max_size=1g inactive=60m use_temp_path=off;

server {
    listen 443 ssl http2;
    server_name api.domain.com;
    
    # SSL Sertifikaları...

    # Security Headers
    add_header X-Frame-Options "SAMEORIGIN" always; # Clickjacking Koruması
    add_header X-XSS-Protection "1; mode=block" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location /api/ {
        proxy_pass http://backend_api;
        
        # Microcaching Aktifleştirme
        proxy_cache my_cache;
        proxy_cache_valid 200 1m; # 200 Başarılı yanıtları 1 dakika cache'le
        proxy_cache_use_stale error timeout http_500 http_502 http_503 http_504; # Backend çökerse cache'deki eski veriyi göster
        
        # Güvenlik başlıklarını proxy altından da geçir
        add_header X-Cache-Status $upstream_cache_status;
    }
}
Bölüm 04

Konteyner Mimarisi, Optimizasyon ve Güvenlik

4.1 İleri Seviye Dockerfile ve Güvenlik Pratikleri

Master Seviye

Docker imajlarınızı oluştururken, root olmayan (non-root) kullanıcılar tanımlamak ve yalnızca derlenmiş binary'leri/kodları kopyalamak çok kritik bir DevSecOps standardıdır.

Golang / Multi-stage / Distroless Dockerfile
# AŞAMA 1: Derleme
FROM golang:1.20-alpine AS builder
WORKDIR /app
# Sistem kütüphanelerine bağımlı olmadan saf statik derleme
ENV CGO_ENABLED=0 GOOS=linux GOARCH=amd64
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN go build -ldflags="-w -s" -o server main.go

# AŞAMA 2: Production (Distroless imaj kullanımı)
# İçerisinde shell (sh/bash) bile barındırmayan ultra-güvenli Google imajı
FROM gcr.io/distroless/static-debian11
# İmajın içine giriyoruz, root kullanıcısı değil nonroot kullanıcısı aktif
USER nonroot:nonroot
COPY --from=builder --chown=nonroot:nonroot /app/server /server
# Sadece çalıştırılabilir dosyayı çağır
ENTRYPOINT ["/server"]

4.2 Docker Compose Ağları, Hacimler ve Log Rotasyonu

İleri Seviye

Varsayılan bridge ağı yerine servisler arası iletişimi izole etmek için özel ağlar tanımlanmalıdır. Ayrıca konteynerlerin sonsuza kadar log üreterek diski doldurmasını önlemek için Docker seviyesinde log-rotasyonu şarttır.

Gelişmiş docker-compose.yml
version: '3.8'

services:
  web:
    image: nginx:alpine
    ports:
      - "80:80"
    networks:
      - frontend      # Sadece frontend ağına dahil
    depends_on:
      - api
    logging:          # Logların diski doldurmasını engelle
      driver: "json-file"
      options:
        max-size: "10m"
        max-file: "3"

  api:
    build: ./api
    networks:
      - frontend      # Nginx ile konuşabilmesi için
      - backend       # Veritabanı ile konuşabilmesi için
    restart: on-failure:5  # Çökerse maksimum 5 kez dene
    read_only: true        # Konteyner dosya sistemini Read-Only yap! (Hacklense bile dosya yazamaz)
    tmpfs:
      - /tmp           # Read-Only olsa da /tmp klasörünü geçici RAM disk olarak ver

  db:
    image: postgres:15-alpine
    networks:
      - backend       # Sadece backend ağına dahil (Nginx ulaşamaz)
    volumes:
      - db_data:/var/lib/postgresql/data
    environment:
      POSTGRES_DB: app_db
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password # Düz metin env yerine Docker Secrets kullanımı

secrets:
  db_password:
    file: ./secrets/db_pass.txt

networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
    internal: true    # Bu ağ dış dünyaya (internete) tamamen kapalıdır!

  db_data:
Bölüm 05

Log Analizi, Systemd ve Modern Sistem İzleme

5.1 Cron'a Modern Alternatif: Systemd Timers

İleri Seviye

Geleneksel cron loglaması zayıftır ve işlemi takip etmek zordur. Modern Linux sistemlerinde zamanlanmış görevler için Systemd Timer'lar kullanılır. Hem saniye bazlı hassasiyet sağlar hem de logları doğrudan journalctl içine atar.

1. /etc/systemd/system/backup.service
[Unit]
Description=Database Backup Script

[Service]
Type=oneshot
ExecStart=/opt/scripts/backup.sh
2. /etc/systemd/system/backup.timer
[Unit]
Description=Run backup every day at midnight

[Timer]
# Her gece 00:00'da çalıştır
OnCalendar=*-*-* 00:00:00
# Sistem o saatte kapalıysa, açıldığında görevi telafi et
Persistent=true

[Install]
WantedBy=timers.target
Aktifleştirmek için: systemctl enable --now backup.timer
Tüm Timer'ları listele: systemctl list-timers

5.2 Journalctl ve Log Veri Madenciliği (Awk/Grep)

Master Seviye

Büyük sunucularda metin tabanlı devasa log dosyaları arasında kaybolmamak için journalctl filtrelerini ve awk metin işlemcisini verimli kullanmak gerekir.

bash
# SSH servisinde dünden bugüne olan "Failed" (Başarısız) kelimesi geçen logları getir
root@server:~# journalctl -u sshd --since "yesterday" | grep "Failed"

# Geçen boot (yeniden başlatma) sırasındaki çekirdek (kernel) hatalarını bul
root@server:~# journalctl -k -b -1 -p err

# Nginx loglarında en çok istek yapan (IP tabanlı) Top 10 IP adresini listele (awk ve sort kombosu)
root@server:~# awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -nr | head -n 10

# Nginx loglarından sadece 404 dönen isteklerin URL'lerini çek
root@server:~# awk '($9 ~ /404/)' /var/log/nginx/access.log | awk '{print $7}'

5.3 Tarihsel Metrikler (sysstat/sar) ve Prometheus

İleri Seviye

htop sadece anlık durumu gösterir. "Dün gece saat 03:00'te sunucu neden yavaşladı?" sorusunun cevabı için sysstat (sar) paketi veya Prometheus & Grafana stack'i kurulmalıdır.

  • sar aracı: apt install sysstat ile kurulur. Arka planda 10 dakikada bir snapshot alır.
  • Prometheus & Grafana: Modern bulut sistemlerinde sunuculara Node Exporter kurularak CPU, RAM, Disk I/O metrikleri merkezi bir Prometheus sunucusuna çekilir ve Grafana panellerinde görselleştirilir.
bash
# Bugünün CPU geçmişini saatlik olarak göster
root@server:~# sar -u

# Ayın 15'indeki RAM kullanım geçmişini göster
root@server:~# sar -r -f /var/log/sysstat/sa15

# Disk I/O (Okuma/Yazma) istatistiklerini izle
root@server:~# iostat -x 2 5  # 2 saniyede bir 5 defa raporla
