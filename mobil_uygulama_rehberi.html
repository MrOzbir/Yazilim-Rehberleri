01. İleri Seviye UI Mimarisi ve Rendering Matematiği

Ekranda gördüğümüz piksellerin arkasındaki Layout Phase, Constraints, ve Side Effect mekanizmalarının işletim sistemiyle olan ilişkisi.

Flutter Engine Layout Constraints

Flutter Rendering Engine: Build, Layout, Paint

Bir uygulamanın akıcı (60/120 FPS) çalışması için Flutter her bir kareyi (frame) 16 milisaniye içinde çizmeli. Bu çizim 4 ana fazda gerçekleşir:

  1. Build Phase: Konfigürasyonların (Widget ağacının) yaratılması. En ucuz fazdır.
  2. Layout Phase (En Kritik Faz): Kimin nerede ve ne kadar büyük olacağına karar verildiği aşamadır. Kural şudur: "Aşağı doğru Constraint (Kısıtlama) iner, yukarı doğru Size (Boyut) çıkar." Ata (Parent) widget çocuğuna BoxConstraints(minWidth, maxWidth, minHeight, maxHeight) gönderir. Çocuk bu sınırlar içinde kendi boyutunu belirler ve atasına bildirir.
  3. Paint Phase: Boyutlar belirlendikten sonra `Canvas` üzerine pikseller çizilir.
  4. Compositing: Farklı katmanların (örn: Opacity, Transform) GPU'ya gönderilmeden önce birleştirilmesidir. RepaintBoundary kullanılarak gereksiz paint işlemleri engellenir.
BoxConstraints Çakışmaları (Unbounded Errors)

Genellikle ListView'i bir Column içine koyduğunuzda Vertical viewport was given unbounded height hatası alırsınız. Bunun sebebi Column'un çocuklarına Sonsuz (Infinity) yükseklik limiti vermesi, ListView'in ise olabildiğince genişlemek istemesidir (Infinity boyut talebi). Çözüm: ListView'i Expanded veya Flexible içine sararak, Column'un ona "sadece kalan alanı al" constraint'i göndermesini sağlamaktır.

// Custom RenderObject Yazmak (En Üst Düzey Performans)
// Sadece Canvas üzerine saf çizim yapan ve Widget maliyeti olmayan yaklaşım
class MyCustomRenderBox extends RenderBox {
  @override
  void performLayout() {
    // Parent'ın constraint'lerine uymak ZORUNLUDUR
    size = constraints.constrain(const Size(100, 100));
  }

  @override
  void paint(PaintingContext context, Offset offset) {
    final paint = Paint()..color = Colors.red;
    // GPU'ya doğrudan çizim komutu
    context.canvas.drawRect(offset & size, paint);
  }
}
Jetpack Compose

Compose Side Effects (Yan Etkiler) Mimarisi

Declarative UI (Compose) fonksiyonları her state değişiminde yeniden çalışır (Recomposition). Eğer bir Composable fonksiyonun içine doğrudan API isteği yazarsanız, her harf yazışınızda state değiştiği için API'ye yüzlerce istek gider. Composable fonksiyonlar Pure (Saf) olmalıdır. Yan etkiler (API çağrısı, Timer, Veritabanı okuması) Effect API'leri ile kontrol edilir.

  • LaunchedEffect: Sadece belirli bir "Key" değiştiğinde tetiklenen Coroutine başlatır. Composable yaşam döngüsüne bağlıdır, ekran kapanırsa istek otomatik iptal edilir.
  • DisposableEffect: Event listener, Broadcast receiver gibi kapanışta (Dispose) bellekten silinmesi (unregister) gereken işlemlerde kullanılır.
  • rememberCoroutineScope: Buton tıklaması gibi callback'ler içinden Coroutine başlatmak için kullanılır.
@Composable
fun SensorScreen(sensorManager: SensorManager) {
    var sensorValue by remember { mutableStateOf(0f) }

    // DisposableEffect: Ekran açıldığında Listener kaydeder, 
    // ekran kapanınca (onDispose) Listener'ı silerek Memory Leak'i önler.
    DisposableEffect(sensorManager) {
        val listener = object : SensorEventListener {
            override fun onSensorChanged(event: SensorEvent?) {
                sensorValue = event?.values?.get(0) ?: 0f
            }
            override fun onAccuracyChanged(sensor: Sensor?, accuracy: Int) {}
        }
        
        sensorManager.registerListener(listener, sensorManager.getDefaultSensor(Sensor.TYPE_LIGHT), SensorManager.SENSOR_DELAY_NORMAL)
        
        onDispose {
            sensorManager.unregisterListener(listener) // Bellek Sızıntısını Önler!
        }
    }

    Text("Işık Sensörü Değeri: $sensorValue")
}

02. İleri Seviye State Management ve Dependency Injection

Güçlü tip güvenliği (Type Safety), değişmezlik (Immutability) ve Bağımlılık Enjeksiyonu prensipleri ile kurumsal yapılandırma.

Immutability Freezed & BLoC

State Immutability (Değişmezlik) ve Freezed Paketleri

State Management sistemlerinin arayüzü güncelleyebilmesi için objelerin bellekteki adreslerinin (Reference) değişmesi gerekir. user.name = "Ali" demek objenin referansını değiştirmez. Bunun yerine objenin kopyasını almalıyız (copyWith). Dart'ta bunu manuel yapmak çok hataya açıktır. Bu yüzden Freezed ve Equatable gibi Code Generation araçları kullanılır.

Union Types ve Freezed Pattern Matching

Freezed sayesinde state'in sadece belirli formlarda (Loading, Loaded, Error) olmasını sağlayabiliriz. UI tarafında when() metodu kullanarak eksik state kontrolü bırakılmasının önüne geçeriz (Derleme zamanı hatası verir).

// 1. Freezed ile State Tanımlaması
@freezed
class ProductState with _$ProductState {
  const factory ProductState.initial() = _Initial;
  const factory ProductState.loading() = _Loading;
  // Başarılı durumda ürün listesi gelir
  const factory ProductState.loaded(List<Product> products) = _Loaded;
  // Hata durumunda mesaj gelir
  const factory ProductState.error(String message) = _Error;
}

// 2. UI Tarafında Tüketimi (Pattern Matching)
Widget build(BuildContext context) {
  final state = context.watch<ProductBloc>().state;

  // Freezed'in 'when' metodu, tüm durumları ele almamızı zorunlu kılar.
  // Bir durumu bile unutursanız IDE kızarır ve derlenmez.
  return state.when(
    initial: () => Text('Arama yapın'),
    loading: () => CircularProgressIndicator(),
    loaded: (products) => ListView.builder(
      itemCount: products.length,
      itemBuilder: (_, i) => Text(products[i].name),
    ),
    error: (msg) => Text('Hata: $msg', style: TextStyle(color: Colors.red)),
  );
}
Riverpod 2.0 DI Container

Riverpod ve Dependency Injection (GetIt/Injectable)

Provider'ın eksikliklerini kapatan Riverpod 2.0, global olarak tanımlanan ama test edilebilir, context'ten bağımsız çalışan bir mimaridir. Riverpod'da özellikle asenkron veriler AsyncNotifierProvider ile çekilir. Kendi içinde Caching, Auto-dispose (ekran kapanınca hafızayı silme) yetenekleri vardır.

GetIt ile Bağımlılıkların Enjekte Edilmesi (DI)

SOLID prensiplerinden 'Dependency Inversion' gereği sınıflar birbirlerini `new` ile yaratmamalıdır. Bunun yerine GetIt gibi bir Service Locator kullanılır. Büyük projelerde bu locatorları elle yazmak yerine injectable paketi kullanılarak annotation'lar (@injectable, @singleton, @lazySingleton) üzerinden bağımlılık grafiği (Dependency Graph) build_runner ile otomatik oluşturulur.

// INJECTABLE KURULUMU (Dependency Injection)
@module
abstract class RegisterModule {
  // Dio instance'ı uygulama boyunca tekil (Singleton)
  @lazySingleton
  Dio get dio => Dio();
}

@lazySingleton
class ApiRepository {
  final Dio dio;
  // Dio, GetIt tarafından otomatik olarak buraya enjekte edilir!
  ApiRepository(this.dio); 
  
  Future<User> fetchUser() async { ... }
}

// RIVERPOD 2.0 ile Async State
@riverpod
class UserNotifier extends _$UserNotifier {
  @override
  FutureOr<User> build() async {
    // get_it üzerinden repository'e eriş ve ilk veriyi yükle
    return getIt<ApiRepository>().fetchUser();
  }

  Future<void> updateUser(String newName) async {
    state = const AsyncValue.loading();
    state = await AsyncValue.guard(() async {
      await getIt<ApiRepository>().updateName(newName);
      return getIt<ApiRepository>().fetchUser();
    });
  }
}

03. İleri Seviye Ağ İletişimi, Veritabanı Motorları ve Bellek Yönetimi

Gerçek zamanlı protokoller, SQLite kilitlenmeleri ve GC (Garbage Collector) çalışma prensipleri.

WebSockets gRPC

REST'in Ötesi: GraphQL, WebSockets ve gRPC

Modern mobil uygulamalar sadece REST API (HTTP GET/POST) ile sınırlı kalamaz. Borsa, sohbet veya canlı konum takibi yapan uygulamalar çok daha efektif protokollere ihtiyaç duyar.

  • WebSockets: Sürekli açık bir TCP bağlantısıdır. Sunucu istemciye, istemci hiçbir şey sormadan veri itebilir (Push). HTTP overhead'i (header'lar) olmadığı için ultra hızlıdır.
  • GraphQL: "Under-fetching" ve "Over-fetching" sorununu çözer. Mobil uygulama (istemci), devasa bir JSON yerine *sadece* ihtiyacı olan alanları (örn: sadece isim ve resim) bir Query ile sunucudan talep eder. Veri tasarrufu sağlar.
  • gRPC (Protocol Buffers): Google'ın geliştirdiği RPC framework'üdür. Veriyi JSON (metin) yerine Binary (ikili) formatta iletir. Serileştirme maliyeti JSON'a göre %80 daha azdır, payload boyutu inanılmaz küçüktür. Özellikle mikroservisler ve yüksek performanslı mobil bağlantılar için geleceğin standardıdır.
SQLite WAL Mode Garbage Collection

SQLite WAL Modu ve Concurrency (Eşzamanlılık)

Mobil veritabanlarında (SQLite/Room/sqflite) sık yapılan hata, arka plan Isolate'i veritabanına devasa bir JSON kaydederken, Main Thread'in o veriyi okumaya çalışmasıdır. SQLite varsayılan olarak Journaling modunda çalışır ve yazma işlemi sırasında tüm veritabanını kilitler (Database Locked Exception).

Bunu çözmek için veritabanı bağlantısı açılırken WAL (Write-Ahead Logging) modu aktif edilmelidir. WAL modu, eşzamanlı olarak 1 okuyucu ve 1 yazıcının veritabanını aynı anda kilitlemeden kullanmasına izin verir. Veriler ana DB dosyası yerine .wal uzantılı geçici bir dosyaya yazılır.

Bellek Yönetimi: Dart GC vs Swift ARC

Dart/Kotlin (Garbage Collector): Dart Generational GC kullanır. Bellek ikiye ayrılır: Young Space (Kısa ömürlü objeler, her frame atılır) ve Old Space (Uzun ömürlü, uygulamanın state'i). GC, referansı kalmayan objeleri arkaplanda temizler.

Swift (ARC - Automatic Reference Counting): GC yoktur. Derleyici compile zamanında objelerin referans sayılarını hesaplar, referans 0 olunca hemen RAM'den siler. Ancak A B'yi, B de A'yı tutarsa (Retain Cycle) referanslar asla 0 olmaz ve kalıcı Memory Leak oluşur. Çözümü weak veya unowned keyword'lerini kullanmaktır.

// SWIFT: ARC ve Retain Cycle Çözümü (Memory Leak Engelleme)
class User {
    var device: Device?
    deinit { print("User silindi") }
}

class Device {
    // EĞER WEAK YAZMAZSAK: User ve Device birbirini güçlü tutar, 
    // ekran kapansa bile RAM'den silinmezler (Memory Leak).
    weak var owner: User? 
    deinit { print("Device silindi") }
}

// Closure içinde weak self kullanımı
fetchDataFromServer { [weak self] data in
    // Eğer istek tamamlanana kadar ekran kapatılırsa, self 'nil' olur 
    // ve crash yaşanmaz, bellek sızıntısı olmaz.
    guard let self = self else { return }
    self.updateUI(data)
}

04. İleri Native Bağlantılar: FFI ve C++ Entegrasyonu

Mobil işlemcinin maksimum gücünü (CPU/GPU) kullanmak için MethodChannel'ı atlayıp donanım diline (C/C++/Rust) direkt inmek.

Dart FFI C++ Entegrasyonu

Dart FFI (Foreign Function Interface) Mimarisi

MethodChannel, mesajları JSON benzeri bir formata serileştirip/deserileştirip yollar (Overhead). Eğer saniyede 60 kare video işleyeceksek, bir OpenCV C++ algoritmasına ihtiyacımız varsa, MethodChannel saniyede 60 devasa array yollarken tıkanır.

Dart FFI, serileştirme yapmaz. Dart ile C++ aynı bellek adresini (RAM Pointer) paylaşır. Dart kodu doğrudan C struct'larına ve Pointer'larına erişir. Sıfır overhead, %100 CPU performansı.

// 1. C/C++ Tarafında Yazılan Fonksiyon (OpenCV Blur örneği)
// extern "C" __attribute__((visibility("default"))) __attribute__((used))
// void apply_blur(uint8_t* image_data, int width, int height) { ... }

// 2. Dart Tarafında FFI Tanımlamaları ve Eşleştirme
import 'dart:ffi' as ffi;
import 'dart:io';

// C dilindeki pointer imzasını tanımla
typedef ApplyBlurC = ffi.Void Function(ffi.Pointer<ffi.Uint8>, ffi.Int32, ffi.Int32);
// Dart dilindeki karşılığını tanımla
typedef ApplyBlurDart = void Function(ffi.Pointer<ffi.Uint8>, int, int);

class ImageProcessor {
  late final ApplyBlurDart _applyBlur;

  ImageProcessor() {
    // Dinamik kütüphaneyi (.so veya .framework) belleğe yükle
    final dylib = Platform.isAndroid
        ? ffi.DynamicLibrary.open('libimage_processor.so')
        : ffi.DynamicLibrary.process(); // iOS statically linked

    // Fonksiyonu bellekteki adresinden bul ve Dart fonksiyonuna çevir
    _applyBlur = dylib.lookupFunction<ApplyBlurC, ApplyBlurDart>('apply_blur');
  }

  void processImage(ffi.Pointer<ffi.Uint8> memoryPointer, int width, int height) {
    // SIFIR GECİKME: Doğrudan C++ kodu çalışır!
    _applyBlur(memoryPointer, width, height);
  }
}
iOS Swift Bridging Header

Objective-C tabanlı eski ve güçlü kütüphaneleri (veya FFI export'larını) Swift tarafında kullanabilmek için Runner-Bridging-Header.h isimli özel bir dosya kullanılır. Bu dosya, C tabanlı kodların Swift derleyicisi tarafından "anlaşılabilir" class/struct'lara dönüştürülmesini sağlayan çevirmendir.

05. Güvenlik İmzaları, ProGuard Matematigi ve CI/CD Pipelines

Hassas kurumsal uygulamaları yayına hazırlamanın zorlu süreçleri: Kod karartma hataları, Uygulama İmzaları ve GitHub Actions YAML yapılandırması.

App Signing ProGuard

App Signing (V2/V3) ve ProGuard Exception'ları

Keystore ve V2/V3 İmzaları

Android uygulamaları (APK/AAB) yayınlanmadan önce Keystore (.jks) ile imzalanır. V1 imzası (JAR signing) kolaylıkla kırılabilirken, APK Signature Scheme v2 ve v3 tüm APK bloğunu kriptografik olarak korur. Eğer APK içine kötü niyetli biri tarafından tek bir byte kod dahi eklenirse imza bozulur ve işletim sistemi "Paket ayrıştırma hatası" vererek kurulumu reddeder.

ProGuard Karartma Hataları (Reflection Crashes)

ProGuard kodu küçültürken kullanılmayan fonksiyonları siler (Tree Shaking). Ancak GSON veya Moshi gibi JSON parse kütüphaneleri, kodun içinde fonksiyonları "Reflection (Yansıma)" ile string isimleri üzerinden bulur. ProGuard bu model isimlerini `a.b.c` yapınca, kütüphane class'ı bulamaz ve uygulama Release modda çöker (Debug modda çalışır).

Çözüm: proguard-rules.pro dosyasına, modellerin ismini değiştirmemesi için "Keep" (tut) kuralı yazılır.

# proguard-rules.pro
# Data sınıflarını (Modelleri) karartma (GSON Reflection için şart)
-keep class com.company.app.models.** { *; }

# Retrofit sınıflarını koru
-keep class retrofit2.** { *; }
-keepattributes Signature
-keepattributes Exceptions
CI/CD GitHub Actions

DevOps: GitHub Actions ile Otomatik Dağıtım (CI/CD)

Büyük ekiplerde "Bilgisayarımdan build alıp Google Play'e atıyorum" devri kapandı. Her Pull Request (PR) açıldığında testlerin sunucuda otomatik koşması ve master branch'e merge edildiğinde uygulamanın markete yüklenmesi gerekir.

Aşağıda tam teşekküllü bir GitHub Actions YAML konfigürasyonu yer almaktadır. Bu script sırasıyla; ortamı kurar, testleri koşar, güvenli keystore'u (base64) çözer, release APK üretir ve Firebase App Distribution / Google Play'e yükler.

# .github/workflows/deploy.yml
name: Android Release Build & Deploy

on:
  push:
    branches:
      - master

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Kodu Checkout Et
        uses: actions/checkout@v3

      - name: Java 17 Kurulumu
        uses: actions/setup-java@v3
        with:
          distribution: 'zulu'
          java-version: '17'

      - name: Flutter Kurulumu
        uses: subosito/flutter-action@v2
        with:
          flutter-version: '3.19.x'
          channel: 'stable'

      - name: Bağımlılıkları İndir (Pub Get)
        run: flutter pub get

      - name: Birim Testlerini Çalıştır (Unit Tests)
        run: flutter test --no-pub

      - name: Güvenli Keystore'u Çöz (Base64'ten .jks'ye)
        run: echo "${{ secrets.KEYSTORE_BASE64 }}" | base64 --decode > android/app/keystore.jks

      - name: AAB Formatında Release Build Al
        run: flutter build appbundle --release --obfuscate --split-debug-info=./debug
        env:
          KEY_STORE_PASSWORD: ${{ secrets.KEY_STORE_PASSWORD }}
          KEY_PASSWORD: ${{ secrets.KEY_PASSWORD }}
          ALIAS: ${{ secrets.ALIAS }}

      - name: Google Play Console'a Yükle (Fastlane Action)
        uses: r0adkll/upload-google-play@v1
        with:
          serviceAccountJsonPlainText: ${{ secrets.GOOGLE_PLAY_SERVICE_ACCOUNT_JSON }}
          packageName: com.company.app
          releaseFiles: build/app/outputs/bundle/release/app-release.aab
          track: internal # Sadece iç test ekibine gönder
Performans Analizi (Jank ve Leak Tespiti)

CI/CD sonrasında uygulama performans testine girer. Flutter DevTools kullanılarak iki şeye bakılır:

  1. Performance Overlay (Timeline): UI Threat ve Raster Threat çubukları 16ms çizgisini aşarsa kırmızı olur (Jank). Çok fazla SaveLayer veya aşırı gölge (Shadow) kullanımı Raster thread'i patlatır.
  2. Memory Leak (Expando): Uygulamada sayfalar arasında gezilir ve "Force GC" butonuna basılır. Eğer heap grafiği sürekli yukarı doğru tırmanıyorsa, kapatılan ekranların nesneleri silinemiyordur (Örn: Dispose edilmemiş AnimationController veya StreamSubscription).
