01. Konteyner Teknolojisi & Docker Anatomisi

Sanal Makineler (VM) vs. Konteynerler

Geleneksel sanal makineler (VM), donanımı hypervisor seviyesinde sanallaştırarak her birine tam bir Guest OS (Misafir İşletim Sistemi) kurar. Bu durum kaynak tüketimini (CPU, RAM, Disk) artırır ve başlatma sürelerini dakikalara çıkarır.

Konteynerler ise çekirdek (Kernel) paylaşımı yaparak işletim sistemi seviyesinde sanallaştırma sağlar. Ortak bir Linux çekirdeği üzerinde sadece uygulamanın gereksinim duyduğu kütüphaneleri izole ederler. Sonuç: Milisaniyeler içinde başlayan, megabaytlar seviyesinde kaynak tüketen bir mimari.

Performans Kazancı: Aynı donanım üzerinde 10 adet VM çalıştırabilirken, yüzlerce Container çalıştırabilirsiniz. Bu yoğunluk, mikroservis mimarisinin temelini oluşturur.

Docker Engine Yapısı

Docker Engine temel olarak üç bileşenden oluşur:

  • Docker Daemon (dockerd): Konteynerleri, imajları ve ağları yöneten arka plan servisidir.
  • REST API: Programların veya Docker CLI'ın Daemon ile konuşmasını sağlayan arayüzdür.
  • Docker CLI (docker): Geliştiricinin komutlarını REST API üzerinden Daemon'a ileten istemcidir.

İmaj (Image) ve Konteyner (Container)

Image: Uygulamanızı, çalışması için gereken ortam değişkenleri, bağımlılıklar ve dosyalarla birlikte paketleyen salt okunur (read-only) şablondur.

Container: Bir Image'ın çalıştırılabilir, izole edilmiş çalışan örneğidir. Üzerine yazılabilir ince bir katman (writable container layer) eklenerek hayat bulur.

Veri Uçuculuğu: Bir Container silindiğinde, writable layer içindeki tüm veriler de kaybolur. Kalıcı veri için mutlaka Volumes veya Bind Mounts kullanılmalıdır.

02. Profesyonel Dockerfile & Katman Optimizasyonu

Temel Dockerfile Talimatları

Bir Dockerfile, Docker Engine'in imajı adım adım nasıl inşa edeceğini (build) tanımlayan manifestodur.

  • FROM: Başlangıç temel imajını belirler. Tüm Dockerfile'lar FROM ile başlamalıdır (argümanlar hariç).
  • RUN: İmaj derlenirken çalıştırılacak shell komutlarıdır (Örn: `apt-get install`). Yeni bir katman oluşturur.
  • COPY: Host sistemdeki dosyaları imajın içine kopyalar.
  • ENV: İmaj ve sonrasında konteyner için ortam değişkenleri tanımlar.
  • EXPOSE: Konteynerin dinleyeceği portu belirtir (Sadece dökümantasyon amaçlıdır, portu dışarı açmaz).
  • CMD / ENTRYPOINT: Konteyner başlatıldığında varsayılan olarak çalışacak ana süreci tanımlar.

Multi-stage Build (Çok Aşamalı Derleme)

İmaj boyutunu (Image Size) dramatik ölçüde düşürmenin en iyi yolu, derleme araçlarını (compiler, SDK) son imajın dışında bırakmaktır. Aşağıda bir Go projesinin Alpine ortamına taşınması örneğini görebilirsiniz.

Dockerfile (Multi-stage) 
# 1. Aşama: Builder (Derleme Aşaması)
FROM golang:1.20-alpine AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o main .

# 2. Aşama: Production (Çalıştırma Aşaması)
FROM alpine:latest
WORKDIR /root/
# Builder aşamasından sadece derlenmiş binary dosyasını alıyoruz
COPY --from=builder /app/main .
EXPOSE 8080
CMD ["./main"]
Distroless İmajlar: Alpine yerine Google'ın geliştirdiği "Distroless" imajları kullanarak, içinde shell (sh/bash) bile barındırmayan, sadece uygulamanızı çalıştıracak kadar minimal ve süper güvenli imajlar elde edebilirsiniz.

Layer Cache Mekanizması & Sıralama Optimizasyonu

Docker, her talimatı bir katman (layer) olarak kaydeder. Bir dosya değiştiğinde, o katman ve sonrasındaki tüm katmanların önbelleği (cache) bozulur ve yeniden çalıştırılır. Bağımlılıkların (package.json, go.mod) koddan (src) önce kopyalanması build süresini saniyelere indirebilir.

Dockerfile (Optimizasyon) 
FROM node:18-alpine
WORKDIR /app

# Kötü Pratik: Tüm kod ve package.json aynı anda kopyalanırsa, her kod değişiminde npm install baştan çalışır.
# COPY . . 
# RUN npm install

# İyi Pratik (Cache-Friendly): Önce sadece package.json kopyalanır.
COPY package*.json ./
RUN npm install --production

# Kod kopyalama işlemi en sona bırakılır. 
COPY . .
CMD ["node", "server.js"]

03. Docker Network & Veri Saklama (Volumes)

Docker Ağ Sürücüleri

  • Bridge (Varsayılan): Aynı makinede çalışan konteynerlerin kendi aralarında konuşmasını sağlayan izole, sanal bir ağdır. Dışarıdan erişim için port yönlendirme (`-p 80:80`) gerekir.
  • Host: Konteyner ile host makine arasındaki ağ izolasyonunu kaldırır. Konteyner doğrudan hostun IP'sini ve ağ arayüzünü kullanır. (Sadece Linux'ta performans artışı sağlar).
  • Overlay: Docker Swarm kümesindeki farklı fiziksel makineler üzerinde çalışan konteynerleri aynı ağdaymış gibi birbirine bağlar.
  • None: Konteynerin ağ bağlantısını tamamen keser (loopback hariç). Maksimum izolasyon sağlar.

Veri Kalıcılığı (Data Persistence)

Konteynerler uçucudur. Kalıcı veriler için üç temel saklama yöntemi bulunur:

  • Named Volumes: Docker tarafından yönetilen, en güvenilir ve önerilen saklama birimidir. `/var/lib/docker/volumes/` altında güvenle saklanır.
  • Bind Mounts: Host makinedeki belirlediğiniz tam bir dosya yolunu (Örn: `/home/user/data`) konteynere bağlar. Host sistemin yapısına bağımlıdır.
  • Tmpfs Mounts: Verileri hostun belleğinde (RAM) tutar, diske yazmaz. Hassas veriler veya hız gerektiren geçici dosyalar için idealdir.

Docker Compose & Çoklu Konteyner Ortamları

Docker Compose, birden fazla konteyneri bir YAML dosyası (`docker-compose.yml`) üzerinden deklaratif (bildirimsel) olarak yönetmemizi sağlayan orkestrasyon aracıdır.

docker-compose.yml 
version: "3.8"

services:
  web:
    build: ./frontend
    ports:
      - "3000:3000"
    networks:
      - app-network
    depends_on:
      - api

  api:
    image: my-backend-api:v1.0
    environment:
      - DB_HOST=database
      - DB_USER=root
      - DB_PASS=secret
    networks:
      - app-network
    depends_on:
      - database

  database:
    image: postgres:14-alpine
    environment:
      POSTGRES_USER: root
      POSTGRES_PASSWORD: secret
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - app-network

networks:
  app-network:
    driver: bridge

volumes:
  db-data:

04. Kubernetes (K8s) Temelleri & Mimari

K8s Control Plane (Master Node) Bileşenleri

Control Plane, kümenin (cluster) beynidir. Global kararları (örneğin zamanlama) alır ve küme olaylarını yönetir.

  • kube-apiserver: Tüm Kubernetes bileşenlerinin birbirleriyle iletişim kurduğu dışa dönük ana API kapısıdır. `kubectl` komutları doğrudan buraya ulaşır.
  • etcd: Kümedeki tüm durum (state) verilerini barındıran, tutarlı ve yüksek erişilebilirlik sağlayan Key-Value (Anahtar-Değer) deposudur.
  • kube-scheduler: Yeni oluşturulan Pod'ların donanım ihtiyaçlarını (CPU/RAM) ve diğer kuralları değerlendirerek, çalışmak için en uygun Worker Node'u seçer.
  • kube-controller-manager: Node'ların çökmesi, replika sayılarının eksilmesi gibi durumları denetleyen ve kümenin istenen durumda (desired state) kalmasını sağlayan kontrolcülerin yöneticisidir.

Worker Node Bileşenleri

İşçi düğümleri, uygulamalarınızın (Pod'ların) fiziksel olarak çalıştığı makinelerdir.

  • kubelet: Master Node'dan gelen talimatları uygulayan ve düğüm üzerindeki Pod'ların sağlıklı çalıştığından emin olan birincil ajan/servistir.
  • kube-proxy: Düğüm üzerindeki ağ kurallarını yöneten, dışarıdan gelen trafiği doğru Pod'lara (Ingress/Service) yönlendiren ağ vekilidir.
  • Container Runtime (CRI): Konteynerleri fiziksel olarak başlatan ve çalıştıran yazılımdır (containerd, CRI-O vb.).

Bildirimsel Yönetim ve `kubectl` Felsefesi

Kubernetes, Emirsel (Imperative - "Bunu böyle yap") komutlar yerine Bildirimsel (Declarative - "Şu durumu sağla") yapıyı benimser.

Declarative Gücü: kubectl apply -f deployment.yaml komutu çalıştırdığınızda K8s'e nasıl yapacağını değil, ulaşılmasını istediğiniz son durumu verirsiniz. K8s mevcut durumu o duruma eşitlemek için tüm aksiyonları kendi kendine alır.
terminal 
# Imperative (Önerilmez, debug için kullanılır):
kubectl run my-nginx --image=nginx --replicas=3

# Declarative (Best Practice):
kubectl apply -f my-deployment.yaml

05. K8s Pods & Yaşam Döngüsü

Pod Anatomisi ve Paylaşım

Pod, Kubernetes ortamındaki en küçük ve en temel dağıtım birimidir. Bir veya birden fazla sıkı sıkıya bağlı konteyneri barındırır. Aynı Pod içindeki tüm konteynerler şu özellikleri paylaşır:

  • Network Namespace: Tüm konteynerler aynı IP adresini ve port alanını paylaşır. Birbirleriyle localhost üzerinden haberleşebilirler.
  • Storage Volumes: Pod seviyesinde tanımlanan depolama alanlarına tüm konteynerler erişebilir.
Sidecar Pattern: Ana uygulamanızın çalıştığı konteynerin yanına, log toplama (fluentd) veya proxy (envoy) amaçlı yardımcı bir konteyner eklendiği yaygın bir tasarım şablonudur.

Yaşam Döngüsü Aşamaları

Bir Pod, oluşturulduğu andan yok edilene kadar çeşitli durumlardan (Phase) geçer:

  • Pending: K8s kümesi Pod'u kabul etti, ancak konteyner imajları indiriliyor veya düğüm ataması (Scheduling) bekleniyor.
  • Running: Pod bir düğüme atandı ve tüm konteynerler yaratıldı. En az bir konteyner çalışıyor durumda.
  • Succeeded: Pod içindeki tüm konteynerler işlemini başarıyla tamamladı ve sonlandı. (Örn: CronJob'lar).
  • Failed: Konteynerlerden en az biri hata ile (sıfır olmayan çıkış kodu) sonlandı.
  • Unknown: Pod'un durumu düğüm ile iletişim kurulamadığı için alınamıyor.

Sağlık Kontrolleri (Probes)

Uygulamalarınızın gerçekten sağlıklı ve trafik kabul edebilir durumda olup olmadığını anlamak için üç tip kontrol mekanizması kullanılır:

  • Liveness Probe: "Konteyner yaşıyor mu?" Uygulama kilitlendiyse, K8s bu kontrolün başarısız olması durumunda konteyneri yeniden başlatır.
  • Readiness Probe: "Konteyner trafik almaya hazır mı?" Uygulama açılırken veritabanı bağlantısı bekliyorsa, hazır olana kadar Service'lerden bu Pod'a trafik gönderilmez.
  • Startup Probe: Yavaş başlayan uygulamalar için diğer procların (Liveness/Readiness) onu öldürmesini geçici olarak engeller.
probes.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: probe-example
spec:
  containers:
  - name: app
    image: my-app:latest
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 3
      periodSeconds: 3
    readinessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10

Init Containers

Ana konteynerler başlamadan önce sırayla ve başarıyla tamamlanması gereken geçici konteynerlerdir.

Kullanım Senaryosu: Ana uygulama başlamadan önce veritabanı şemasını oluşturmak (migration) veya bir servisin (Örn: veritabanı) hazır olmasını beklemek için initContainers mükemmel bir çözümdür.

06. Deployments, ReplicaSets & Ölçeklendirme

Deployment ve ReplicaSet Anatomisi

Doğrudan Pod oluşturmak yerine her zaman bir Deployment kullanılır. Deployment, arka planda bir ReplicaSet yönetir; ReplicaSet ise Pod sayısının her zaman istenen düzeyde (desired state) olmasını garantiler.

  • Rollout: Uygulamanın yeni bir versiyonu (yeni imaj) yayınlandığında, yeni bir ReplicaSet oluşur ve trafik yavaşça oraya kayar.
  • Rollback: Yeni versiyonda bir hata varsa, K8s saniyeler içinde eski ReplicaSet'e geri dönme imkanı sunar (kubectl rollout undo).

Güncelleme Stratejileri

Deployment nesnesi uygulamayı kesintiye uğratmadan güncellemek için gelişmiş stratejilere sahiptir:

  • RollingUpdate (Varsayılan): Pod'lar sırayla kapatılıp yenileri açılır. Bu süreçte maxSurge (geçici olarak limitin ne kadar üstüne çıkılabileceği) ve maxUnavailable (kaç Pod'un aynı anda kapalı olabileceği) parametreleri kullanılır.
  • Recreate: Yeni versiyona geçmeden önce tüm eski Pod'lar anında silinir. Geçici bir kesinti (downtime) yaşanır, ancak versiyon çakışmaları önlenir.
deployment.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: nginx:1.24
        ports:
        - containerPort: 80

Yatay Ölçeklendirme: HPA (Horizontal Pod Autoscaler)

Trafik arttığında uygulamayı ayakta tutmak için otomatik ölçeklendirme gerekir. HPA, donanım metriklerini (CPU, RAM) izleyerek veya özel metriklerle Pod sayısını dinamik olarak artırır/azaltır.

Metrik İzleme: HPA'nın çalışabilmesi için kümenizde metrics-server kurulu olmalı ve Pod'larınızda mutlaka CPU/RAM resources.requests tanımları yapılmış olmalıdır.

07. K8s Ağ Dünyası: Services & Ingress

Service Soyutlaması ve Kube-proxy

Pod'lar fani (geçici) varlıklardır; her silinip açıldıklarında IP adresleri değişir. Service objesi, bu değişken Pod'ların önünde sabit bir IP ve DNS adı sağlayan soyut bir yük dengeleyicidir.

Arka planda her Node üzerinde çalışan kube-proxy, iptables veya IPVS kuralları aracılığıyla Service'e gelen trafiği ilgili Pod'lara yönlendirir.

Service Türleri

  • ClusterIP (Varsayılan): Sadece küme içinden (internal) erişilebilen, sabit bir IP sağlar.
  • NodePort: Tüm Node'ların statik bir portunu (Örn: 30000-32767) dışarıya açarak trafiği Service'e yönlendirir.
  • LoadBalancer: AWS, GCP gibi bulut sağlayıcılarının yük dengeleyicilerini (Cloud LB) entegre ederek uygulamayı dış dünyaya açar.
  • ExternalName: CNAME kaydı gibi davranarak Service'i dışarıdaki harici bir DNS ismine bağlar.
service.yaml 
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
spec:
  type: ClusterIP
  selector:
    app: frontend
  ports:
    - protocol: TCP
      port: 80
      targetPort: 3000

Ingress ve Ingress Controller

Service türleri genellikle 4. katmanda (TCP/UDP) çalışır. Ingress ise 7. katmanda (HTTP/HTTPS) çalışarak host tabanlı (domain.com) ve yol tabanlı (/api, /web) gelişmiş trafik yönlendirmesi, SSL sonlandırma (SSL Termination) ve yük dengeleme sağlar.

Ingress objesinin çalışabilmesi için kümede bir Ingress Controller (Nginx, Traefik, HAProxy vb.) çalışıyor olmalıdır.

ingress.yaml 
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: main-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: myapp.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: backend-api
            port:
              number: 8080
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-web
            port:
              number: 80

08. Kalıcı Veri Yönetimi (PV, PVC, StorageClass)

Kalıcı Depolama İhtiyacı

Konteynerlerin efemer (geçici) doğası, veritabanları veya dosya sunucuları gibi kalıcılık (persistence) gerektiren stateful uygulamalar için bir problemdir. Pod silindiğinde tüm veriler yok olur. Kubernetes, depolama mimarisini soyutlayarak bu sorunu çözer.

Mimaride Sorumluluk Ayrımı: PV ve PVC

K8s, depolama sistemlerinde yönetim ve kullanım süreçlerini birbirinden ayırır:

  • PersistentVolume (PV): Altyapı yöneticisi (Admin) tarafından kümeye eklenen fiziksel depolama birimidir (NFS, AWS EBS, Local Disk). Pod'ların yaşam döngüsünden bağımsızdır.
  • PersistentVolumeClaim (PVC): Geliştiricinin uygulama için talep ettiği depolama miktarı ve erişim modu bildirimidir (Örn: "Bana 10GB Okunabilir/Yazılabilir bir disk ver").
Eşleşme Süreci (Binding): Bir PVC oluşturulduğunda K8s arka planda, bu talebi karşılayacak kapasite ve modlara sahip boş bir PV arar ve bunları birbirine bağlar.

StorageClass ve Dinamik Üretim (Dynamic Provisioning)

Bulut ortamlarında yöneticilerin manuel olarak PV yaratması hantaldır. StorageClass, bir PVC talep edildiğinde arkada yatan bulut API'sini tetikleyerek otomatik (dinamik) olarak diskin ve PV'nin yaratılmasını sağlar.

pvc-pod.yaml 
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
  storageClassName: standard

---
apiVersion: v1
kind: Pod
metadata:
  name: mysql-db
spec:
  containers:
  - name: mysql
    image: mysql:8.0
    env:
      - name: MYSQL_ROOT_PASSWORD
        value: "secret"
    volumeMounts:
      - name: mysql-storage
        mountPath: /var/lib/mysql
  volumes:
    - name: mysql-storage
      persistentVolumeClaim:
        claimName: mysql-pvc

09. ConfigMaps & Secrets ile Ayar Yönetimi

12-Factor App Prensibi

Modern yazılım geliştirme standartlarına (Twelve-Factor App) göre, uygulamaların kaynak kodu (Source Code) ile çalışacağı ortama ait konfigürasyonları (Config) birbirinden kesinlikle ayrılmalıdır. K8s bu ayrımı sağlamak için ConfigMap ve Secret objelerini sunar.

ConfigMap: Ortam Değişkenleri ve Dosyalar

Hassas olmayan verileri (veritabanı host adresi, log seviyesi, Nginx konfigürasyon dosyaları vb.) saklamak için kullanılır. Pod'lara iki yöntemle enjekte edilebilir:

  • Environment Variables (Çevre Değişkeni): Uygulamanın process.env üzerinden doğrudan erişebileceği değişkenler.
  • Volume Mounts (Dosya): Bir JSON veya Conf dosyasının sanal bir disk olarak Pod içine yerleştirilmesi.
configmap-pod.yaml 
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "debug"
  API_ENDPOINT: "https://api.internal.com"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-demo-pod
spec:
  containers:
  - name: my-app
    image: my-app:latest
    envFrom:
      - configMapRef:
          name: app-config

Secret: Hassas Verilerin Saklanması

Şifreler, veritabanı bağlantı dizesi (Connection String), TLS sertifikaları veya API tokenları gibi kritik verileri tutmak için tasarlanmıştır. Veriler Base64 algoritması ile kodlanarak saklanır.

Güvenlik Uyarısı (Security Note): K8s Secret'ları varsayılan olarak şifrelenmez (encrypt edilmez), sadece Base64 formatında encode edilir. Bu yüzden Secret objelerinizi düz metin halinde Git deponuza (GitHub/GitLab) KESİNLİKLE pushlamayın. Git ortamı için SealedSecrets, SOPS veya External Secrets (Vault) kullanılması endüstri standardıdır.
secret.yaml 
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  # "secret123" kelimesinin base64 hali: c2VjcmV0MTIz
  db-password: c2VjcmV0MTIz

10. Gelişmiş K8s Objeleri (StatefulSets, DaemonSets, Jobs)

StatefulSet: Kararlı Mimariler

Stateless (durumsuz) uygulamalar için Deployment kullanılırken, PostgreSQL, MongoDB, Kafka gibi veritabanı veya mesaj kuyruğu sistemleri için StatefulSet şarttır. StatefulSet şu iki kritik avantajı sağlar:

  • Kararlı Ağ Kimliği (Ordinal Index): Pod'lar rastgele hash'ler yerine db-0, db-1, db-2 şeklinde numaralandırılarak açılır. Pod ölse bile yeniden açıldığında aynı ismi alır, bu sayede Master-Slave mimarileri kurulabilir.
  • Kararlı Depolama: volumeClaimTemplates kullanılarak her Pod'a ayrı ve kendine özel bir kalıcı disk (PVC) otomatik atanır.

DaemonSet: Her Node'a Bir Pod

Bir uygulamanın kümedeki istisnasız tüm Node'larda (veya belirli etiketlere sahip Node'larda) tam olarak bir kopyasının çalışmasını garanti eden objelerdir. Node sayısı artarsa DaemonSet otomatik olarak yeni Node'a da bir Pod yerleştirir.

Kullanım Senaryoları: Merkezi log toplama ajanları (Fluentd, Promtail, Filebeat) ve Node seviyesinde donanım metriklerini izleyen araçlar (Prometheus Node Exporter) için idealdir.

Job ve CronJob: Operasyonel İşler

Sürekli çalışan servisler yerine, bir işi yapıp tamamlandığında kapanan (çıkış kodu 0 veren) objelerdir.

  • Job: Tek seferlik, tamamlanana kadar çalışan operasyonlar. (Örn: Veritabanı Migration scriptleri). Başarısız olursa Pod'u tekrar tetikleyebilir.
  • CronJob: Job objelerini standart Linux Cron formatında (Örn: 0 2 * * * - Her gece saat 02:00) zamanlayarak çalıştıran yapılardır. Periyodik yedeklemeler için kullanılır.
cronjob.yaml 
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup-worker
            image: backup-script:v1
          restartPolicy: OnFailure

11. Helm Charts ile Kubernetes Paket Yönetimi

Helm Nedir?

Kubernetes ortamları için apt, yum veya npm gibi düşünebileceğiniz resmi paket yöneticisidir. Yüzlerce satırlık karmaşık Kubernetes YAML dosyalarını tek bir parametre dosyası (values.yaml) ile yönetilebilir, sürümlendirilebilir paketler (Chart) haline getirir.

Helm Chart Mimarisi

Bir Helm Chart projesi oluşturduğunuzda (helm create my-app) standart bir dizin yapısı oluşur:

  • Chart.yaml: Paketin versiyon, isim ve bağımlılık (dependencies) bilgilerini tutan manifesto dosyasıdır.
  • values.yaml: Kullanıcının değiştirebileceği tüm değişkenleri (Örn: replicaCount, image tag, port) tutan ana yapılandırma dosyasıdır.
  • templates/: İçerisinde Go-Template motoru kullanılarak yazılmış taslak YAML dosyalarını barındırır. (Örn: replicas: {{ .Values.replicaCount }}).

Helm Temel Komutları ve Operasyonlar

Helm, sadece kurulum değil, bir uygulamanın tüm yaşam döngüsünü yönetir:

terminal 
# Yeni bir proje iskelesi oluşturur
helm create my-webapp

# Helm deposundan bir hazır paket indirir ve kurar
helm repo add bitnami https://charts.bitnami.com/bitnami
helm install my-db bitnami/postgresql

# Kendi yazdığınız Chart'ı values dosyasındaki değişkenlerle günceller
helm upgrade my-webapp ./my-webapp -f custom-values.yaml

# Herhangi bir hata durumunda bir önceki çalışan sürüme geri döner
helm rollback my-webapp 1

12. GitOps & CI/CD Konteyner Entegrasyonları

GitOps Felsefesi (Push vs Pull Modeli)

Geleneksel CI/CD sistemlerinde (Jenkins, GitLab CI vb.), boru hattı (pipeline) kodu derler, imajı üretir ve son aşamada kubectl apply komutunu dışarıdan K8s'e gönderir (Push Modeli). Bu güvenlik riskleri ve durum uyumsuzlukları yaratır.

GitOps yaklaşımı ise Pull Modeline dayanır. Git deposunu "Tek Doğruluk Kaynağı" (Single Source of Truth) olarak kabul eder. Küme içerisinde çalışan bir ajan (ArgoCD veya Flux), Git deposunu sürekli izler ve küme ile Git arasındaki farkı bulup eşitler.

Drift Resolution: GitOps mantığında, eğer birisi sunucuya sızıp komut satırından Pod sayısını 5'e çıkarırsa, ArgoCD hemen fark edip "Git deposunda bu 3 olarak yazıyor" diyerek sistemi otomatik olarak 3'e geri çeker (Self-healing).

Eksiksiz Bir Modern CI/CD/GitOps Akışı

Bugün endüstri standardı olarak kabul edilen modern uygulama dağıtım akışı şu şekilde işler:

  • 1. CI Aşaması (Sürekli Entegrasyon): Geliştirici kodu yazar ve GitHub'a Pushlar. GitHub Actions tetiklenir, birim testleri (Unit Tests) koşar, Docker imajını (Örn: v1.0.1) derler ve Docker Hub'a (Registry) yükler.
  • 2. Config Güncellemesi: Aynı CI pipeline'ı, ayrı bir Git deposunda tutulan Helm veya Kustomize dosyalarındaki image_tag değerini v1.0.1 olarak günceller ve commit atar.
  • 3. CD Aşaması (GitOps): Kubernetes kümesi içinde yaşayan ArgoCD, bu repodaki değişimi 3 dakika (varsayılan) içinde fark eder. Mevcut K8s durumuyla senkronize (Sync) işlemini başlatır ve yeni Pod'lar devreye alınır.
